# way の精細化のラウンド

決まり（くどさの物差し、部品の画面での大きさ、本体の描き方、道具の癖）は [docs/reference/way-addon.md](../../../docs/reference/way-addon.md) にある。**作業の前に、11 章（くどさの物差し）・12 章（部品の画面での大きさ）・8 章（道具の癖）を読む。**
ここには進め方だけを書く。部品を足す作業そのものは [way-addon-build](../way-addon-build/SKILL.md)、つなぎ目の位置合わせは [way-calibration](../way-calibration/SKILL.md) を見る。

流れの元の決めごと（名前の分け方・比べ方・評価の観点）は issue #56 にある。回した例は AMI の記録（`docs/records/2026-11-20_ami-refine-round1.md`〜`round8.md`）。

## 進め方の原則

- **1 ラウンドは構造の試し。** 値の微調整だけで回さない。対象の「意味の木」（何が何でできているか）を作り、葉ごとに「描く・誇張する・省く・形を変える」を試す。値の調整は、構造を決めた後の仕上げにだけ使う
- **前のラウンドと同じ条件で比べる。** 撮る場所・保存データ・拡大率・測り方を固定し、ラウンドの版（`<元の名前>_round<n>`）を前の版と同じゲームに並べる
- **ループの中でユーザーの判断を待たない。** 判定は物差し（数値と手本）と画面の比べで AI が行う。判断できない点は途中で止めずにためておき、ラウンドの終わりにまとめて報告する
- **セルだけで良しとしない。** 行き止まり・壁のある版・坂・雪など、ゲームの中で隣と組み合わさる所はゲームの画面で見る
- **ラウンドの版は本番の絵を変えない。** 試しは `src/`・`dist/`・共有の `tools/blender/sheetlib` を変えずに作る。本番に入れるのはユーザーの指示があったときだけ
- **止める合図。** ほとんどの区画が前と「同じ」になった、または くどさで「悪くなった」が出始めたら、続ける価値があるかをユーザーに報告する

## 1 ラウンドの手順

### 1. 直す所を探す

- issue（AMI は #44 など）の候補と、前のラウンドの報告で残した点を見る
- 画面を読むエージェントの指摘は確度が低い（リファレンス 8.3）。全区画を目で読むより、シートの輪郭の差（`sheet_diff.py`）と `sheet_audit.py` で、新しい欠けやはみ出しが入っていないことを確かめる
- 共通の部品（`tools/blender/sheetlib`、アドオンの共通部品）を直すときは、先に、ほかのアドオン（blender-poc・ほかの way）への巻き添えが無いかを確かめる

### 2. 意味の木を作り、葉を選ぶ

1. 対象を部品に分ける（例: 線路 → 道床〔肩・のり面・砕石〕・まくらぎ・レール〔頭・側面〕・汚れの帯・雪）
2. 各部品の画面での大きさ（px）を書く（リファレンス 12 章）。1〜2px にしかならない部品は、誇張するか省くかを決める
3. 現実の部品の一覧と、描いたか・省いたかを付ける（写実の評価に使う）
4. このラウンドで試す葉を選ぶ。前のラウンドの報告で残した点を優先する

### 3. 葉ごとに試す

1. ラウンドの版の設定に、葉ごとの試しの鍵（例: `7snow3`・`7endtrim3`）を足す。AMI は系統（`AMI_FAMILY`。`rail_ballast`・`rail_slab`・`tram`・`road`）ごとに分かれ、在来線は `addons/ami/blender/round.py` の `ROUND_SETTINGS`、ほかは `blender/round_<系統>.py` の `ROUND_SETTINGS` と `apply`。**土台は今の本番の `render.py`。** 本番に入れ済みのラウンドの設定を重ねると二重にかかる（`round.py` の冒頭に書いてある）。共有の `sheetlib` の値をモジュールごと書き換えない
2. 鍵を指定して、その葉に関係するシートだけ描く（AMI は `AMI_FAMILY=<系統> AMI_ROUND=<鍵> python -X utf8 ../../tools/blender/render_parallel.py --entry blender/round.py <対象>`。系統の対象は `AMI_FAMILY=<系統> python -X utf8 blender/round.py --targets`）
3. 前の版と同じセルを並べ、最近傍で 4〜10 倍に拡大して比べる（`zoom.py`、`hcat.py`）。地面の色の背景（雪なら地面の雪の色）に置いて見る
4. 葉ごとに「採る／採らない」と理由を一言で決める。採らない試しも記録に残す（寸法で直らないと分かったことも知見）

### 4. ラウンドの版を作って撮る

1. 採った葉を合わせたラウンドの設定（`ROUND_SETTINGS["<n>"]`）で対象一式を描き、pak にする（AMI は `AMI_FAMILY=<系統> python -X utf8 blender/round.py <n>` で `rounds/ami_<系統>_round<n>.pak`。在来線だけ `rounds/ami_round<n>.pak`）。ラウンド 0 は描かずに pak だけ作る（今の `src/` の絵）
2. 見本をゲームで撮る（AMI は `SUFFIX=_round<n> EXTRA_PAKS=<ラウンドの pak> bash ingame/sample_parallel.sh`、見本は `NUT=` で系統のものを選ぶ。見本が `SUFFIX` を引けないときは、`sample.nut` の `wdx` と同じ作りを足す）。種類違い（AMI はスラブ軌道の `TRACK=`）にも効く変更なら、その見本も撮る
3. 前のラウンドの画面と画素で比べ、違いが出た区画だけを拡大して見る。変えていない区画に差が出たら、共通部品の巻き添えを疑う
4. くどさを撮って測る: 前のラウンドと今のラウンドを並べて `ingame/calib_capture.sh`（`WAYS_NUT`・`PAKS`・`PORT`、見本は `NUT=`）、`busy_measure.py` で測る。判定と雪の扱いはリファレンス 11 章。物差しの境は在来線の温暖の絵で合わせたもので、ほかの way には前のラウンドからの動きと手本の幅で判定し、「物差しが無い」ことを判断できない点として報告する

### 5. 評価する

前のラウンドと比べて、観点ごとに「良くなった／同じ／悪くなった」と理由の一言を書く。点数にしない。

| 観点 | 見るもの |
|---|---|
| ① 欠陥 | 欠け・はみ出し・段・すき間。輪郭の差・`sheet_audit.py`・ゲームの画面。前より増えたらそのラウンドは不合格 |
| ② 写実 | 意味の木の部品の一覧に対して、描いた・省いた |
| ③ くどさ | 物差し（リファレンス 11 章）の値と前のラウンドからの動き |
| ④ そろい | 版（基盤・高架・橋・トンネル・壁）・気候・向き・種類の間で、同じ部品の描き方がそろっているか |

### 6. 記録して報告する

1. 記録を書く: `docs/records/YYYY-MM-DD_<アドオン>-refine-round<n>.md`（目的、葉ごとの試しと判断、ラウンドの版、評価の表、分かったこと）。比べた画像はアドオンの `docs/` に置き、記録から名前で引く
2. 新しく確かめた決まり（部品の大きさ、道具の癖、物差しの扱い）はリファレンスに足す
3. ラウンドの pak（`rounds/`）・設定・記録・画像をローカルでコミットする。push・PR はユーザーの指示を待つ
4. ユーザーに報告する: 評価の表、比べた画像（`SendUserFile`）、ためておいた判断できない点。issue へのコメントは指示があったときだけ

## 本番に入れる（ユーザーの指示があったとき）

1. ラウンドの設定を、本番の描き分け（AMI は `render.py` の種類ごとの設定）に写す。ラウンドの版がモジュールの値を書き換えていた所は、`sheetlib` に引数や関数の口を足して置き換える（既定の絵は変えない）
2. 本番で描いたシートを、ラウンドの版のシートと画素で比べる。違いが出たら、意図した直しか、写し漏れかを決める
3. 変えていないはずのシート（ほかの種類・壁・橋脚、blender-poc）を描き直し、前とバイト単位で同じことを確かめる
4. `sheet_audit.py` を前と比べ、増えた印が新しい欠陥でないことを確かめる
5. 見本をゲームで撮り直す（種類違いも）。行き止まり・壁のある版・坂は必ず見る
6. 本番の絵をラウンドの版と並べて測るときは、描かずに pak だけ作る（AMI は `python -X utf8 blender/round.py <n>`）。検証環境に入っているユーザーの pak を上書きしない
7. README（アドオンの今の状態）と、ラウンドの版の作りの注記（二重にかからないこと）を直す。記録を書き、ローカルでコミットする

## ゲームを動かすときの決まり

- 起動・操作はスクリプトと MCP だけで行う。ユーザーが遊んでいるゲーム（別のポート）は止めない
- AMI の `sample_parallel.sh`・`calib_capture.sh` は、検証用のフォルダの写し（`work/parallel/`・`work/calib_game/`）でゲームを起動し、撮り終えたら閉じて写しを消す。検証用のフォルダには書き込まない。手でゲームを閉じるときは、プロセスの実行ファイルの場所が写しの中であることを確かめてから閉じる
- 検証用のフォルダに何かを置いたときは、置いたもの・消したものをユーザーに報告する

## 系統を並べて回すとき

- 系統ごとに別のセッション（別の worktree）で回してよい。各セッションが書くのは、自分の系統のラウンドの設定・見本・記録・画像だけにする。本番の `render.py`・共有の `sheetlib`・README・リファレンスは、本番に入れる段で 1 つずつ直す
- 同時に動かすときは、描く数と台数とポートを分ける: `SHEET_JOBS`（1 回で描く Blender の数。マシン全体の上限は `render_parallel.py` が共有の描画の枠で守る。`tools/README.md` の「描画が遅いとき」）、`sample_parallel.sh` の `JOBS`（ゲームの台数）と `BASE_PORT`（`JOBS` 以上離す）、`calib_capture.sh` の `PORT`。合計が CPU のスレッド数を大きく超えないようにする
