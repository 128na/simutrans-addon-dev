# way アドオンの知見（本体の描き方・dat の決まり・手本の作り）

線路・道路・側壁・高架・橋・トンネルなどの way 系アドオンを作って分かった「決まり」をまとめる。
本体（Simutrans）と手本（pak128 標準・SIS・iss）の作りを、ソース・画像・ゲームで確かめたもので、このリポジトリのコードを読んでも分からない。

- 作業の手順は書かない。手順はスキル（[way-addon-build](../../.claude/skills/way-addon-build/SKILL.md)・[way-calibration](../../.claude/skills/way-calibration/SKILL.md)・[way-refine-rounds](../../.claude/skills/way-refine-rounds/SKILL.md)）にある
- 調べた経緯は書かない。経緯は `docs/records/` と各アドオンの README にある
- 各項目に「どこで確かめたか」と、数値には測った日付を書く。新しい手本・新しい本体では測り直す

## 2. 本体の描き方と持ち分（どの画素をそのタイルが描くか）

本体は地面を先にまとめて描き、物を奥から描く。カメラは南東にある。

- **平らな部分**: 持ち分は地面の菱形。奥のタイルが手前へはみ出した絵は、手前の平らな地面が先に描かれるので、約 1 行（＋半行）までしか残らない。
  持ち分を 2 行以上ずらすと、継ぎ目に草の線が出る。坂のタイルは地面を後から描き直すので、奥からのはみ出しを消す
- **高さのある部品**（壁・躯体）: 持ち分の全体を上へ広げる。奥のタイルの絵の上に出る（建物と同じ）。
  タイルの境の切り口の面は取る（残すと暗い縦線になる）。輪郭の半透明の画素は捨てる（黒い点線になる）。
  取った口からは壁の中（影で暗い）が見え、隣のタイルの壁が後から描かれないと残る。斜めのタイルの手前の絵は隣の行き止まりの奥の壁の絵より後に描かれ（セルを 1 枚ずつ重ねて切り分けた経験則。本体のソースの描画順とは突き合わせていない）、
  画面で縦向きの斜めの壁の口が 1px の暗い縦線で見えた。その壁だけ裏面を描かずに描く（口が透明になる）。端の壁と画面で横向きの斜めの壁は、
  口から見える暗い色が切り口の面の代わりになっているので変えない（`sheetlib` の `cull_diag_wall_ends`。[記録](../records/2026-11-21_ami-wall-diag-end-seam.md)、2026-11-21）
- **坂の下・床の下が見える絵**: 平地に立つ坂（橋の Ramp）は坂の面から地面まで、坂から始まる橋（Start）は地面を下げた形、高架は床から既定の高さ（pak128 は 2 段）下の地面まで（5 章の表）
- **坂の面より下を描かない絵**: トンネルの坑口は坂の面だけ（と躯体の高さだけ上）。way や坑口の絵は地面の上に重なるので、
  隣の丘に隠れるはずの面（坑口の高い側の辺の下）まで持ち分に入れると、丘の上にはみ出して見える
- **隣の way とつながる絵**（坑口・橋の端など）: 持ち分の手前の 2 辺は線路と同じ量だけ広げ、つながる部分（床・基盤）は
  隣と同じ基準面に乗せて、タイルの辺まで伸ばす。どれか 1 つ欠けると辺に 1 画素おきのすき間が出る
- **手前/奥**: 東西の線路は北が奥、南北の線路は西が奥。斜めは東寄りが手前。T字は、まっすぐ通る線路に対して決める。
  本体の部品の頂点からは測らない（頂点の多い部品を足すと入れ替わる）。経路が 1 本なら中心線の中心、複数ならタイルの中心から、壁の範囲の中心を測る。行き止まりの端の壁は線路の外へ向く向きで決める（`sheetlib` の `near_frame`・`near_camera`。[記録](../records/2026-11-19_near-camera-path-centre.md)、2026-11-19）
- **斜めのタイルの並びと、画面で縦向きの斜めの継ぎ目**（2026-11-24、#217）: 斜めの way（`diagonal[...]` の 1 枚の絵）は、曲がりのタイルが交互に並んで 1 本の斜めになる。
  地面の菱形は幅 128・高さ 64 で、`ami_canal_scenic` を `(x,y)=(0,0)` から `(4,4)` へ `command_x.build_way` で敷くと（AMI の `ingame/canal_diag_probe.nut`、`OTRPv64`、`flat_512_left_v64`、2026-11-24。景観の運河は今は斜めの絵を持たないので、並びを見るときは `ami_canal` に替える。`get_dirs` の値は絵に関係しない）、通った 9 タイルの `get_dirs()` は
  `(0,0)=2`（行き止まり）・`(1,0)=12`・`(1,1)=3`・`(2,1)=12`・`(2,2)=3`・`(3,2)=12`・`(3,3)=3`・`(4,3)=12`・`(4,4)=1`（行き止まり）。
  12（南＋西）が `diagonal[sw]`、3（北＋東）が `diagonal[ne]` の絵で、タイルの画面の位置は `((x−y)·64, (x+y)·32)` なので、
  画面で縦向きの斜めは `sw` のタイルが右の列（間隔 64 行）、`ne` のタイルが左の列（`sw` から 32 行ずれ、間隔 64 行）に交互に並ぶ。
  `sw` の絵は地面の菱形の左半分（頂点が左）、`ne` は右半分（頂点が右）で、2 枚の三角が互いの縦の辺をはさんで 1 本の縦の帯になる（別のタイルの三角がすき間を埋める）。
  同じ向きのタイルは 64 行ごとに並ぶので、壁の高さ・水面の深さで三角を下へ広げると（景観の運河は 13px）、縦の辺は 64 行より長くなり、1 つ下のタイルの三角と重なる。
  `diagonal[close1]`・`[close2]` は 2 本の斜めを 1 枚に描いた絵（`close1` は `nw` と `se` の 2 つの帯、`close2` は `ne` と `sw` の 2 つの帯）。
  **壁を持つ部品は、画面で縦向きの斜めで 2 つの問題が出る**（景観の運河、2026-11-24）: (1) 壁が画面の縦の線になって内側の面が見えず、直線の壁（面が見える）とのつなぎ目で壁・笠石の見え方が連続しない。(2) 隣のタイルの壁が落とす影が自分のセルの水面にも掛かるので、壁を自分のタイルの内側だけで切ると、影の縦の範囲が組のセルでずれ、64 行ごとに明るい楔（横線）が出る（壁を長く取ると楔は消えたが、(1) は残った）。
  iss の運河（`../refs/iss/src/way/water/canal.dat`）は `diagonal` を持たず、`image[sw]` などを L 字のカーブのセル（行 2 の列 5〜8）にして、斜めを L 字のジグザグにしている。AMI の景観の運河もこれに合わせた（`ami_dat.py` の `NO_DIAG`。壁・水面が直線と同じ作りなので連続する）
  iss の運河の行き止まりのセル（`canal.dat` が指す `canal_kt` は、同じフォルダの `canal.png` を読んだ。行 0 の列 5〜8）は、閉じた側に平らな蓋（笠石と同じ明るい面）をかぶせ、水が蓋の下へ消える暗渠になっている（2026-11-24 に絵を読んだ）。AMI の景観の運河は、タイルの半分を蓋にすると広すぎたため（ユーザーの指摘）、辺に、笠石・護岸（辺から 0.35）より 0.1 広い（辺から 0.45）まぐさを付けて、その下に暗い口を描く作りにした（だまし絵）
  （壁を長く取って影をそろえる直し（c17394e）は、(1) が残るので #217 で取り下げた）。
- **予想図との差が 0 px** であっても、分かるのは「各タイルが持ち分どおりに描かれている」ことだけ。絵どうしが段差なくつながっているかは別に見る

## 3. 手本の作り（2026-11 時点）

- **SIS・pak128 標準の道路**: 菱形を地面より 1px 下にずらして描き、自分の上の 1 行は奥のタイルのはみ出しで埋める。
  合わせるときは、絵と持ち分を一緒に 1px 下げ、手前の縁を半行広げる
- **線路の新描画位置**（今の pak128・iss）: 下がっているのはレールだけで、道床は地面の位置にある。斜めの絵はタイルの中心に描かれている。
  道床まで下げると、画面で縦向きの斜め（sw・ne）との角に段が出る。道床は地面の位置を基準にし、レールとまくらぎを下げる（横向きの斜めは半分）。
  ただし道床をまったく下げないと、レールが道床の下寄りに見える。blender-poc では道床も 2px 下げて、Rail_100 と同じく道床の中心がレールより約 1px 下になるようにした
- **SIS の新幹線の線路は旧描画位置**（2026-11-22、#26）: レールは地面の位置にある。基準面を動かさず（`datums=R.FLAT`）、持ち分を手前へはみ出させない（`spill=0`）で描いた AMI の旧版（`ami_rail_<種類>_old`）は、SIS（`SIS_ST_TGbl_E01-999B`）と東西・南北の直線・斜めでレールが段なくつながった（`seam_judge.py`、継ぎ目の草 0px）。新描画位置の版は、同じ継ぎ目でレールが数 px 下にずれて見えた。壁・架線は基準面 `bed`（新は 2px 下）に合わせて描かれるので、旧の基盤・高架には旧用の壁・架線・橋脚が要る（[記録](../records/2026-11-22_ami-old-draw-position-seam.md)。`addons/ami/ingame/seam_slope_check.sh`・`old_seam.sh`）
- **「Rail_100 は道床ごと 4px 下」ではない**（思い込みが外れた例）。重心は道床の幅や陰で 1〜2px 動くので、レールの位置は明るさの断面で比べる
- **斜めの幅**: 道床・車道・白線は、経路からの距離を直線の 1/√2 にすると、タイルの辺で直線と同じ点を通る
- **Rail_100 が手前の継ぎ目**（2026-11-13）: Rail_100 の道床は奥の辺の近くで上の数行が欠けていて、奥のタイルのはみ出しで埋める作りらしい。
  持ち分を菱形どおりに切った線路が奥に来ると、帯の上側に草の線（15〜28px）が出る。奥側の持ち分を手前の 2 辺へ 1 行と半行はみ出させると埋まる。
  相手の作りに合わせてはみ出しを足すと、他の相手（SIS・道路）との継ぎ目も変わりうる
- **Rail_100 は `ImageUp2` を持たない**。急坂には 1 段の坂の絵が出る
- **pak128 標準の線路のカーブは斜めの絵**（2026-11-17、`../refs/pak128/infrastructure/rail_tracks/rail_100_tracks.dat`）: `Image[NE]` などが `Diagonal[NE]` と同じセルを指す。T字は直線と、枝の 2 辺をつなぐ斜めの直線 2 本、十字は直線 2 本と斜め 4 本で、間の道床は埋まっている。分岐の絵（`NSE1` など）は直線と斜め 1 本
- **坑口の形**（pak128）: タイル全体の箱で、屋根は丘の上面
- **iss の跨座式モノレール**（2026-11-22、`../refs/iss/src/way/monorail/straddle.dat` と配布物の `straddle_g.png`・`straddle_e_<版>.png`）: 地上の版は桁だけで、幅は約 0.85、上面は地面から約 0.7（画面の帯 11px）、下面は地面。高架の版は桁がタイルを出入りする辺ごとに、その辺の角に柱を立てて辺の中点の桁の下へ腕を渡す。front は南・東の側、back は北・西の側、center は両側。カーブは斜めの絵、近い斜めのキーと雪の絵は無い。pak128.japan の跨座式の車両は車体の下端が地面の高さに描かれ、裾が桁を隠す（ゲームで確認。AMI の README の「跨座式モノレールの作り」）

## 4. 厚みのある絵を画面で下げるときの坂（2026-11-13）

形を手前へ動かして下げると、坂では動いた先の高さが変わり、同じ量でも画面の下げ幅が変わる（手前上がりの急坂で 0.5 倍、手前下がりの急坂で 1.5 倍）。

- レールと道床で動かし方を変えると、坂の向きでレールが道床の片側に寄り、急坂でまくらぎが道床に埋もれる
- どの部品も坂を当てる前に動かす。下げ幅は「地面の上での位置のずれ」（平地と同じ量を動かす。辺で隣と同じ点を通る）と
  「形の高さ・基準位置を打ち消す分」（坂の傾きで割り戻して、画面でちょうどその px）に分ける
- 全部を割り戻すと、急坂と平らなタイルの継ぎ目で道床の縁に 1px の段が出た
- 坂の向きで帯の高さが変わる（急坂の奥側は平地の半分）。px の値は同じ向きの坂どうしか、平地との差で比べる

## 6. 側壁・基盤・バリエーションの作り

- 名前の末尾は `single`（両側）・`back`（奥だけ）・`center`（なし）・`front`（手前だけ）。iss・SIS と同じ並べ方
- 壁: 経路から一定の距離の両側。斜めも同じ作りにする（タイルの辺で直線の壁と同じ点を通る）。
  分岐・十字は、ほかの経路の通り道に入る部分を削る（先の経路の壁を残し、重なった切れ端を消す）
- 基盤: 壁のある側は壁で止まり、壁のない側はタイルの端まで埋まる。経路ごとの板を足し合わせる作りは、分岐で壁を突き抜けた
- 行き止まり: 車止め + 端の壁（タイルの幅いっぱいに作り、残した側壁の外側を削る）。並べると 1 つのコの字になる
- 1 タイルだけの軌道: 全面の基盤だけ（すき間埋めの景観用）
- 高架: 側壁の版 + 橋脚 + 床の下の躯体。橋脚は既定の高さ（pak128 は 2 段）下の地面まで描く
- 近い斜め: 壁の無い版（本体・旧・試作）と道路・高速道路は `diagonal[close1]`・`[close2]` を持つ。道路は斜めの 2 片を中心線で切って 1 枚に描く（片を中心線より広げると、2 片の歩道の面が重なる）。側壁・高架の版は持たせない。持たせると分け合うタイルが十字 1 本の way になり、奥と手前が同じ版になって 2 本の間に壁が立つ。持たせなければ本体が 2 本の way を置くので、奥の線を back、手前の線を front にできる
- 斜めの基盤の壁の無い側: 中心線から TILE/(2√2)（近い斜めの 2 本の真ん中）より外を削る。タイルの角まで塗ると、隣の線のレールを隠し、隣の線の壁の外へ三角に突き出した。切り口は下ほど中心線へ寄る斜めにする。縦に切ると、奥の線の切り口の側面（暗い）が手前の線の床の上に線で見えた（2026-11-14、ゲームで確認）
- 高架の back・center の斜めには橋脚を描かない。手前にいつも front の線があり、その橋脚で足りる。描くと、画面で横向きの斜めでは柱が手前の線の床に暗い点線で見えた
- 画面で横向きの斜め（`nw`・`se`）では、手前の壁・手すり（`frontdiagonal`）がその線のレールを隠す。壁から外へずれても画面では縦にしか動かず、壁の高さ（約 9px）がレールとの間（約 7px）より大きいため。1 本だけでも同じで、車両を走らせても絵の欠けや重なりは出なかったので、このままにした（2026-11-14、ユーザーが確認）
- 版を切り替えて敷く順（2026-11-15、`blender-poc` の `track_review.nut` で確認）: 敷いてあるタイルに別の版を敷くと、本体はそのタイルの way の版を新しい版に置き換える（スクリプトの `build_way` は Ctrl を押した扱いで、速さが同じでも置き換える。`simtool.cc` の `tool_build_way_t`、`bauer/wegbauer.cc` の `build_track`）。直角カーブで back の直線と front の直線をつなぐとき、つなぎ（角の手前と角の 2 タイル）を後から敷くと、角の手前のタイルまでつなぎの版になり、back と front が逆に見える。つなぎを先に敷き、直線で角の手前のタイルを上書きする。後から敷いても置き換わらないことがあったので（同じ見本で、降雪側の側壁だけ）、敷いた後に角と手前のタイルの版を確かめる
- 複線の直角のカーブの版（2026-11-21、在来線の基盤の版と壁・架線つきの壁、iss の `iss_wtg_0240_*` で確認。[記録](../records/2026-11-21_ami-double-curve-base.md)）: 基盤の版のカーブのセルは、画面で横向き（`nw`・`se`）なら back が経路の下・front が上を埋め、縦向き（`sw`・`ne`）なら back が経路の右・front が左を埋める。画面で右と左に曲がる角では、外の線と内の線の版が角の前後で入れ替わる（直線の絵は向きだけで選ばれるので、線の途中で版を替えることは避けられない）。角のタイルを南北の辺の版にすると 4 方向ともつながり、東西の辺の版にすると右・左の角に草の穴が開く。画面の道具では、way は Ctrl なしでも速さが同じなら置き換わり（`simtool.cc` の `tool_build_way_t` は Ctrl なしで「速い way を残す」。残すのは今の way の方が速いときだけ。`bauer/wegbauer.cc` の 2906〜2915 行付近）、壁（way-object）は Ctrl なしだと前の版のまま向きだけ足される（`simtool.cc` の 4723 行付近、`obj/wayobj.cc` の `extend_wayobj`。OTRP `d19f266f6`）。なので way は東西の辺を先に敷いて南北の辺で角を上書きし、壁は南北の辺を先に敷く。画面の道具では試していない
- 渡り線を敷くと経路のタイルの版が替わる（2026-11-21、AMI の `ingame/crossover_wall.nut` で確認。`OTRPv64_3.exe`）: 並べた線の間に渡り線を敷くと、渡り線の経路のタイル（両端の T字と、渡り線の端の直線のタイル）の way が、渡り線を敷いた way に置き換わる。線路の道具は Ctrl を押さなくても、既存の way が新しい way より速いときだけ残す（`simtool.cc` の `tool_build_way_t`、3301 行付近の `set_keep_existing_faster_ways(true)`。置き換えの判定は `bauer/wegbauer.cc` の 2905〜2915 行付近）ので、同じ速さの版どうしでも置き換わる。版の基盤が壁の側を壁で止める作り（AMI）では、置き換わったタイルに草の帯と、壁の外へはみ出す基盤が出る。iss の線路は基盤がどの版もタイル全体を塗る（壁は架線の way-object に入っている）ので、置き換わっても見えない（`../refs/iss/release/pak128/way/rail/standard_concrete_g_<版>.png` の直線と T字のセル）。渡り線の後に本線をそれぞれの版で敷き直すと戻る
- 高速道路の側壁（2026-11-14、`blender-poc` で確認）: 手本は iss の都市高速 `wrg_0120_*`（タイルの端に立つコンクリートの壁）。線路と同じ 4 つの版で、壁の選び方も同じ。複数車線は外側の車線に back・front、内側に center を敷く
- 高速道路の高架: 床（路面と基盤）がタイルいっぱいなので、線路と同じ中央の柱は床に隠れて見えない。柱を道の全幅（両側の壁の下）まで長くすると、床の縁の下に見える。基盤の上面を路面の板と同じ高さにすると重なって基盤の色が出るので、路面の板の厚みより下げる
- 高速道路の橋: 線路の橋と同じセルの並びと dat のキーで作れる。手本の iss の都市高速の橋は床の縁が青い桁だが、基盤の側面を青くしても壁の真下に隠れ、ゲームではほとんど見えない（桁を壁の外へ出す必要がある）
- 壁を way-object に分けた道路の行き止まり（2026-11-19、AMI の道路の高架で確認）: way の絵の白線をタイルの辺まで引くと、白線の端が、別に描いた端の壁の下の縁から 1px 出て明るい点に見える。壁を焼き込む版は壁の外側を削る型で消えるが、分けた版は way の絵に壁が無いので消えない。白線は端の壁の内側の面（経路の始点）で止める
- 道路の壁と基盤の版（2026-11-19、AMI で確認）: 地上の道路は路面がタイルいっぱいなので、直線・T字・十字・坂・1 本の斜めは、通常の版に壁の way-object を重ねるだけで合う。合わないのは 2 つ。複線の直角の曲がりでは、通常の版のカーブ（斜めの絵をタイルの半分で切ったもの）の間に草の三角が出る。近い斜めでは、通常の版が近い斜めの絵を持つので分け合うタイルが way 1 本になり、壁が十字の絵になる（10 章）。どちらも、近い斜めの絵を持たず、カーブを斜めの形の別のセルに描いて壁の無い側をタイルの端まで延ばした基盤の版（iss の `iss_wrg_0120_*` と同じ持ち方）で直る。高架の複線の直角の曲がりも、カーブを斜めのセルのままにすると三角の穴が開く
- 高速道路の橋の桁（2026-11-19、AMI で確認）: 基盤とその下の桁を青くし、壁の外の面まで出す（躯体のように内へ下げない）と、壁の下に約 4px の帯で見える。iss の `iss_br_0120_bridge1` の帯も 4px
- 高速道路のトンネル: 手本の iss の都市高速の坑口は、線路の坑口と同じタイルいっぱいの箱に、口の上の名板を付けたもの。穴は両側の壁の内側まで広げる
- 線路の汚れ（色だけの薄い帯。2026-11-15、`blender-poc` で確認）: レールの周りの汚れは走行面（レールと同じ基準面）に乗せる。新描画位置では走行面が路盤より約 2px 手前にずれるので、
  路盤に乗せると汚れがレールとずれる。そのずれのため、行き止まりでは帯の端を少し詰めないと道床の外へはみ出す。
  雪の絵では汚れを消さず、雪の上の汚れ（灰色）にした（道床が雪に埋もれるので、汚れも雪の上に出す）
- 汚し（ウェザリング。2026-11-22、#154）: コンクリートの材質 `sheetlib` の `tiled_concrete_material` に、`tint`（色の倍率）・`streak`（縦の面に縦の筋の雨だれ）・`grime`（`grime_z` の高さの範囲で下ほど暗くする地際の汚れ）がある。既定では掛からない。模様はタイルの 1 辺を周期にするので、タイルの辺でつながる。同じ灰色の物どうしは、色味（`tint`）の差がいちばん等倍で見分けやすかった。雨だれは等倍では細かいざらつきに見えた。AMI のモノレールは、暖かい灰と地際の汚れで第 1 弾の高架・橋脚と見分ける（ユーザーの決定。[記録](../records/2026-11-22_ami-monorail-weathering.md)）
- 部品の位置は、部品ごとに足し引きせず、乗る基準面（路盤・走行面）に持たせる
  （レールと道床を別々のやり方で動かして、急坂でまくらぎが道床に埋もれた）

## 7. 継ぎ目の自動判定の限界（2026-11-13、道路の絵をわざと 2px 下げて確かめた）

- 2px のずれは、こちらが手前の継ぎ目に出る草の線（23〜43px）で不合格になった
- 模様のずれは、2px 下げても 1.0〜1.5px にしか出なかった（帯を斜めに横切って測るので小さく出る）。模様だけで不合格になるのは、それより大きなずれ
- 中心のずれは、両側の縁が測れて幅がそろう（差 3px 以下）ときだけ当てになる。坂と平地の継ぎ目は参考（坂の帯は手本でも 6px 広く測れる）。
  歩道付きの道路・全面の道床（縁がタイルの角まで届く）、曲がり（片側の縁しか測れない）、幅の違う相手でも参考値。
  幅の違う相手（Rail_100 は道床が広い）では、中心の差は段ではなく作りの違い
- 草の色は、緑が赤・青より 12 以上、青より 40 以上大きい画素とした。歩道の緑がかった敷石は草にしない。地面の違うマップでは確かめ直す
- 一つの継ぎ目には「相手が奥・こちらが手前」と「こちらが奥・相手が手前」の 2 種類がある。はみ出しの決まりが違う相手だと、片方だけに草の線が出る
- 坂の十字の、坂の斜め隣の角のタイルは、予想図が「坂は地面を後から描く」ことを再現していないので、差が出てもゲームの画面が正しいことがある

- 描画（Python）: `sheetlib/__init__.py` は部品の関数を、モジュールと同じ名前で出す（`monorail_parts` など）。`import sheetlib.monorail_parts as MP` はモジュールでなく関数を返し、`MP._M_MONO_BEAM = ...` は黙って関数の属性になる。モジュールは `sys.modules["sheetlib.monorail_parts"]` から引く（2026-11-22、#154。[記録](../records/2026-11-22_ami-monorail-weathering.md)）
- ゲームのスクリプト（Squirrel）: `local a = d[1], b = d[2];` のように 1 つの `local` で 2 つ以上を宣言すると、2 つ目以降に違う値が入った（`b` が 2 になった。MCP の `run_squirrel`、`OTRPv64_3.exe`、2026-11-21）。`local` は 1 つずつ書く
- 描画: `noisy_material`（まだらの材質）は、`material()` の自己発光（`emit`）を引き継がない。`material(...)` で作った一色の材質（例: AMI の白線 `MARKING_LINE` は発光 0.35）を、`noisy_material` のまだらに替えるときは、同じ `emit` を渡す。渡さないと、同じ色の範囲でも灰色に沈み、1px の線が薄く見える（`addons/ami/blender/render.py` の `MARKING_LINE_WORN` で、色を 0.62〜0.84 にしても、発光を付けるまで元より暗いままだった。ゲームで前後を撮って確かめた。2026-11-23、#197）
- 描画: 並列描画（`render_parallel.py`）で、対象ごとのアイコン・カーソルの後処理（`icons.py --own`）が同時に動く。`icons.py` の文字の一時ファイルが全プロセス共通の名前（`work/_icon_text.png`）だったため、取り合って札の字が欠けたり別の対象の絵が混ざったりして、並列に描いた回だけシートがコミット済みと違った（2026-11-24、Blender 4.5.16、#244。#229 の高架 3 枚も同じ原因の可能性が高い。未確認）。今はプロセスごとの名前（`_icon_text_<PID>.png`）。新しく一時ファイルを書く道具は、対象や PID の入った名前にする（[記録](../records/2026-11-24_parallel-render-icon-text-race.md)）
- 描画: `sweep` は折れ線の角で断面を細める（角の前後の向きの平均で断面を向けるので、90° の角では横幅が 1/√2）。L 字のように角を直角に折りたい経路は、`core.MiterPath` で渡す（`sweep` が角で断面の幅を保つ。白線・走行跡・路肩の雪の型が角で細らず、辺に届く）。ふつうの経路は変わらない。AMI の生活道路のカーブ（L 字）が使う（2026-11-24、#259。[記録](../records/2026-11-24_ami-road-curve-arc-ell.md)）。円弧のセルは、タイルの角を中心に半径がタイルの半分（2 辺の中点をつなぐ）で、辺で直線・T字・十字と白線の位置がそろい、路面軌道の曲線と同じ中心・半径で重なる

### 8.3 画像を読んで判定するときの限界（2026-11-19）

直線の線路の合成画像で、Sonnet・Opus・Fable を比べた結果（[記録](../records/2026-11-19_image-check-model-comparison.md)）。問題数が少なく、分岐・高架などは試していない。

- 3 倍（最近傍）に拡大すると、2 × 2px の欠け、幅 6px・高さ 2px のはみ出し、1px のずれを 3 モデルとも全問見つけた
- 等倍では 2 × 2px の欠けをどのモデルも見つけられなかった。Sonnet は 1px のずれを、はみ出しと取り違えた
- 1 タイルだけ 6% 明るい違いは、3 倍でもどのモデルも見つけられなかった。20% の違いは 3 倍なら全問見つけた
- 欠陥の無い画像を、欠陥ありと誤って答えたものは無かった

## 9. 分岐（switch）の絵（OTRP 専用）

T字・十字の way に、通常の絵のほかに「分岐の向きを示す絵」を持たせる仕組み。標準の Simutrans には無く、OTRP（KU-TA 由来のソース）の本体だけが読む。
本体のソースで確かめたもの: `descriptor/writer/way_writer.cc`・`descriptor/reader/way_reader.cc`・`descriptor/way_desc.h`・`boden/wege/weg.cc`・`boden/wege/schiene.cc`。
詳しい経緯は OTRP 本体の PR（`128na/simutrans` の `feature/switch-image-override`、フォーク元 `teamhimeh/simutrans#810`）にある。

### 9.1 dat のキーと絵の番号

| dat のキー | 絵の番号 | 本体の呼び方 |
|---|---|---|
| `image[nse1]` `image[new1]` `image[nsw1]` `image[sew1]` `image[nsew1]` | 16–20 | switch 画像（`nw` = false） |
| `image[nse2]` `image[new2]` `image[nsw2]` `image[sew2]` `image[nsew2]` | 21–25 | switch 画像（`nw` = true） |
| （makeobj にキーが無い。pak への継ぎ足しで入る） | 26–30 / 31–35 | ex 画像（`nw` = false / true） |

- 方角の並びは `nse`・`new`・`nsw`・`sew`（T字 4 種）と `nsew`（十字）。手前の絵（`frontimage[...]`）と雪（`[1]`）も同じ並び。
- `image[new2]` が dat にあると makeobj は 26 枚（通常 16 + 分岐 10）を書き、無いと 16 枚で分岐の絵なしになる。**1 と 2 の 10 枚をそろえる**（片方だけ書くと、もう片方は空の絵になる）。
- 本体の判定は枚数だけ。16 枚を超えると switch 画像あり、26 枚を超えると ex 画像あり（`way_reader.cc`）。waytype は問わない。
- ex 画像（26–35）は本体が読むが、`way_writer.cc` のキーは `nsew2` までなので、makeobj の dat からは書けない。
  本体の動作確認には、キーを `nse3`〜`nsew4`（検証用の仮の名前）まで足した makeobj を別に作って使った。本物のキー名は決まっていない。
- 専用の makeobj が無くても、標準の makeobj で作った pak に画像ノードを継ぎ足せば ex 画像を入れられる（OTRP の分岐画像を選べるビルドで確認。2026-11-19、[記録](../records/2026-11-19_way-ex-image-pak-graft.md)）。
  - 提供用の way を makeobj で作り、`image[nse1]`〜`image[nsew2]`（16–25 番）に ex 画像を割り当てる。その 10 ノードを、対象の way の同じ種類の画像リストの末尾へ写す。写す順がそのまま 26–35 番になる。
  - 直すのは画像リストごとに 2 か所: ノードの見出しの子の数と、ノードのデータ先頭の `count`（どちらも uint16）を 36 にする。親のノードには長さの欄が無いので、ほかは変えない。
  - 写す画像リストは way の子ノードの番号で、雪なしは 2（奥）・6（手前）、雪ありは 2（奥）・6（奥の雪）・9（手前）・12（手前の雪）。雪の有無は way ノードの `number_of_seasons` で分かる（位置はノードの版 6・7・8 で 27・35・36 バイト目。makeobj 60.12 の Windows 版は版 8 を書いた）。
  - pak にキー名は入らず、本体は番号だけを見る。36 番以降も足せて読み込めるが、どの処理からも引かれない。タイルの詳細の選択肢は標準・分岐 1・2・ex 3・4 と自動で固定なので、増えない。
- ex 画像を書ける makeobj は公開されていない（2026-11-14 に確かめた）。
  - `teamhimeh/simutrans` のリリース（v63_3 まで）の添付はゲーム本体だけで、makeobj は無い。
  - OTRP のソースの makeobj は本家 Simutrans 125 の makeobj 60.12 と同じで、キーは `nsew2` まで。
  - KUTA 版の配布物（v6、2021-12-12）もゲーム本体と ja の tab だけで、makeobj は無い。README の分岐の説明は `NSE1`〜`SEW2` の 8 枚だけで、ex には触れない。
- ex 画像の由来: 読む処理と自動で選ぶ条件（9.4）は、`KU-TANS/simutrans` の `53ca75e21`（2021-12-12、KU-TA-Server「KUTA_v6 source」）で初めて現れる。
  KUTA v1〜v6 の改造を OTRP（`37dfb76a8`、2021-03-31）の上に 1 コミットでまとめたもので、それより細かい履歴は公開されていない（KU-TANS の他のブランチ・リポジトリにも無い）。
  本家の Simutrans には無い。同じコミットの makeobj も 26 枚までで、書く側は作られていない。
- 本体が見るのは絵の並び（26 番から `26 + ribi_to_extra + nw * 5`）だけで、キー名は makeobj の中で決まる。
  書く手段が無かったので、既存の pak で使われたキー名がある見込みは低い。それでもキー名を決める前に、OTRP の開発者に一言確かめる。

### 9.2 本体での使われ方

| 場面 | 内容 |
|---|---|
| 自動選択 | 線路（tram を含む）と道路の T字・十字だけ。隣のタイルの形から選ぶ（`select_switch_image`・`select_switch_road_image`）。ほかの waytype には自動選択がない |
| 列車の予約 | 線路は、曲がる経路を取る列車が予約すると、その向きの switch 画像に切り替わる（`schiene_t::reserve`）。固定した分岐は切り替わらない |
| 固定（OTRP の機能） | タイルの詳細ダイアログで、switch 画像を持つ分岐の画像を選べる。選択は保存され、形が変わる・分岐が解消すると自動に戻る。画像が無い選択肢は出ない |

ダイアログの名前と絵の対応。名前の向きは、タイルの中に描かれるカーブが主線のどちらの端につながるか（枝が主線のどちら寄りに出るか）。
ゲームに方角の表示は無いが、画面は地図ごと回るので、方角は画面の向きに固定される（北 = 右上・東 = 右下・南 = 左下・西 = 左上）。ダイアログの名前には画面の向きを添える（例: 「東（右下）へ分岐」）。
自動選択（`select_switch_image`）が `nw` の真偽を選ぶ条件は「隣のタイルがどちらへ曲がるか」で、タイル内のカーブはその手前側（S 字の前半）を描く。
隣の向きで名前を付けると、画面のカーブと逆になる:

| ダイアログの名前 | 絵 |
|---|---|
| 標準 | 通常の絵（`image[nse]` など） |
| 南（左下）へ分岐／北（右上）へ分岐（NSE） | `image[nse2]`（南–東のカーブ）／`image[nse1]`（北–東） |
| 西（左上）へ分岐／東（右下）へ分岐（NEW） | `image[new2]`（西–北）／`image[new1]`（東–北） |
| 北（右上）へ分岐／南（左下）へ分岐（NSW） | `image[nsw2]`（北–西）／`image[nsw1]`（南–西） |
| 東（右下）へ分岐／西（左上）へ分岐（SEW） | `image[sew2]`（東–南）／`image[sew1]`（西–南） |
| 十字（左右が直進）／十字（上下が直進）（十字） | `image[nsew2]`／`image[nsew1]`（2 系は画面の左の角から右の角への線が直進、1 系は上の角から下の角への線が直進。`way_writer.cc` のコメントの「北西–南東が直進」は 1 系） |
| Y字分岐・三方分岐・複線渡り線 A／B（ex） | ex 画像（dat からは作れない。pak への継ぎ足しは 9.1。選ばれる形は 9.4） |

T字のカーブの向きは、blender-poc の見本（`ingame/switch_auto.nut`）でゲームの自動選択を 8 通りとも確かめた（2026-11-14）。十字の 2 つは、blender-poc の絵をゲームのダイアログで見て確かめた（2026-11-14）。ずれていたらこの表と本体のラベル（`gui/ground_info.cc`）を直す。

確認の状況（単色の簡易画像で、標準 = 灰・状態 1 = 青・状態 2 = 赤を割り当てて、ゲームで確かめた）:

| waytype | 結果 |
|---|---|
| rail | 実際のアドオンで確認（選択・保存・ロード・形の変化で自動に戻る） |
| tram・monorail・maglev | 実際のアドオンで確認（OTRP 本体の作者による） |
| road・water（運河）・air | 本体のツールで T字・十字とも選択でき、選択ごとに別の絵になることと、詳細ダイアログの表示を確認。air は誘導路（`system_type=0`）と滑走路（`1`）の両方 |
| ex 画像（road・rail） | 検証用 makeobj で 36 枚の way を作り、選択肢 3・4 が別の絵になることと、詳細ダイアログの表示を確認。dat の `3` 系は選択肢 4、`4` 系は選択肢 3 |
| air の滑走路（`system_type=1`） | 本体の建設が T字を許さない（`bauer/wegbauer.cc`: 滑走路は直線と十字の交差だけ）。分岐の絵は十字にだけ使われる |
| 電力（power） | 対象外。電線は `leitung_t`（`obj_t` 派生）で `weg_t` ではないため、この機能の対象にならない |

### 9.3 絵の作りと確かめ方

- 1 と 2 は左右反転ではなく、T字なら枝の曲がる側の違い。持ち分は通常の絵と同じ（2 章）。
- 線路の T字の 1・2 で、タイルの中に描くカーブの向きは 9.2 の表のとおり（枝が隣のタイルでどちらへ曲がるかで選ばれ、タイルの中はその手前側のカーブ）。
- 線路の十字の 1・2 は自動では選ばれない（`select_switch_image` は T字 4 種だけを見る）。タイルの詳細で固定したときだけ出る
- 変えるのは走行面（まくらぎ・レール）だけにし、道床・側壁・基盤は通常の T字・十字と同じにする。
  片側のカーブだけで全部を組むと、カーブの内側に丸い壁が立ち、隣のタイルとつながらない（blender-poc の側壁の版で確認、2026-11-14）
- 道路の自動選択は「隣に T字がある」条件で switch 画像（`nw` = false）を使う（`select_switch_road_image`）。線路と意味が違うので、道路用の絵を作るときは `boden/wege/weg.cc` の条件を読んで合わせる。
  - **OTRP v64 では `select_switch_road_image`（KUTA 流の決まり）は無くなった**（teamhimeh/simutrans#816）。上の説明は v63 以前の本体の話。v64 の自動選択は線路と同じ決まり: 十字は標準の十字の絵（多車線の十字もふさがらない）、T字は枝の隣がカーブのときに分岐 1・2。固定の道具では、T字に 1・2、十字に `nsew1`・`nsew2` を選べる。AMI の道路で確かめた（左側通行の `flat_512_left_v64.sve`、`sim-WinGDI64-OTRPv64.exe`、`ingame/road_sample.nut` の区画 H・I・L・M、2026-11-23、#46。右側通行は未確認）
  - 呼び分けは `weg_t::calc_image`（`OTRP-KUTAv6` の `boden/wege/weg.cc` 732〜739 行）。斜め・近い斜めでなく、dat が switch 画像を持つ way だけで、`track_wt` なら `select_switch_image`、`road_wt` なら `select_switch_road_image`（988 行〜）。この部分は `MULTI_THREAD` と `COLOUR_DEPTH` が 0 でないビルドでだけ働く（`#if`）。
  - 道路の T字（たとえば `nse`）は、枝の隣（東）が三方分岐で、本線の両隣（北・南）が三方分岐でないときに `image[nse1]`（`nw` = false）になる。2 本の道路を隣り合わせに並べて渡り口でつないだ形が当たる。本線の隣が三方分岐のときは、ex 画像があればそちら、無ければ通常の T字。三方分岐の判定（`ribi_t::is_threeway`）は十字も含む。
  - 道路の十字は、ex 画像が無い way では、隣のどれかが T字か十字のとき、その隣の向きの T字の switch 画像の `nw` = true（東なら `image[nse2]`、西なら `image[nsw2]`、北なら `image[new2]`、南なら `image[sew2]`。この順に見る）を十字のタイルに出す。つまり道路の T字の「2」は、自動では十字のタイルにだけ出る。T字の形に描くと、十字の 4 本目の腕の側が閉じて見える（AMI の道路の見本の区画 L、2026-11-19）。隣を見る順が東 → 西 → 北 → 南で、最初に見つけた向きだけで決まるので、道路を 3 本以上並べた交差点や、南北・東西とも並べた交差点では、どの十字もほぼ `nse2`・`nsw2` になり、東西に並べた向きは使われない（AMI の `ingame/road_junction_sample.nut` で 2×4〜6×6 の 8 通りを敷いて読んだ。2×4 だけ `sew2`・`new2`、2×6 は `sew2`・`new2`・`new2`、6×6 はどの行も `nse2 nse2 nsw2`。`OTRPv64_3.exe`、2026-11-19）。「2」に向きのある絵（停止線など）を描くと、2 本の組を 1 本が横切る形でしか合わない（AMI の見本で停止線を描いて確かめた。2026-11-19）。「2」を十字の絵にすると、T字のタイルを固定の道具で「2」にしたときもその十字の絵が出る（1 枚の絵を、自動の十字と固定の T字の両方に使うため。AMI の `road_sample.nut` の区画 I、2026-11-19）。「2」を T字の形にすると、多車線の十字で横切る道路の側に路側線が出る（同じ見本の区画 L）。1 枚の絵で両方は満たせない。ex 画像がある way では、十字の 1・2 や ex 画像を選ぶ別の条件になる（下の「ex 画像を足したとき」）
  - 道路の 1・2 の使われ方のまとめ（`boden/wege/weg.cc` の `select_switch_road_image`、988〜1165 行。`128na/simutrans` の `feature/script-save` で読んだ。2026-11-20）: 自動では、「1」は T字のタイルで、枝の先の隣が三方分岐（T字か十字）のときだけ出る（989〜1093 行）。4 車線（道路 2 本）に 2 車線の道路が T字でつながると、奥の T字のタイルに出る。「2」は T字のタイルには自動では一度も出ず、十字のタイルにだけ出る（ex 画像が無い way は 1145〜1160 行）。名前の向き（`nse2` なら東）の隣が交差点の続きになっている十字、という意味になる。つまり道路の 1・2 は T字の分岐の向き（線路の分岐器の意味）ではなく、KUTA 版から引き継いだ多車線の交差点のための絵で、固定の道具の名前（線路の分岐の意味）とは合わない。斜め・近い斜めの道は分岐の絵を選ぶ処理に入らない（732 行）
  - ex 画像を足したとき（`weg.cc` 1106〜1142 行）: ex 画像がある道路の十字は、隣の十字が 2 方位（東と南、東と北、西と北、西と南のどれか 1 組）なら十字の 1・2 か ex の十字を出す。それ以外（隣の分岐が 1 方位だけ、または向かい合う 2 方位を含む）は、ex が無いときと同じく T字の「2」を出す。十字が 2×2 に並ぶ 4×4 の交差点は直るが、1×2 に並ぶ 4×2 と、3×3 に並ぶ 6×6 の中の列・行はふさがったまま（コードを読んだ結果。ex 画像はゲームで足して確かめていない）。ex 画像があると、多車線の T字路の T字のタイルにも ex の絵が出る（1002〜1011 行など）

  - 道路の十字を固定するときの選択肢（`feature/switch-image-override` の `gui/ground_info.cc`）は、値 1「十字（左右が直進）」が `image[nsew2]`、値 2「十字（上下が直進）」が `image[nsew1]`。言葉は線路の絵（タイルの角を結ぶ直線。9.2 の表）に合わせたもので、道路の南北・東西の軸（画面ではどちらも斜め）とは対応しない

### 9.4 ex 画像が自動で選ばれる線路の形

本体の条件は `boden/wege/weg.cc` の `select_switch_image` と `boden/grund.cc` の `is_use_track_wt_ex_image`（どちらも 9.1 の KUTA_v6 のコミットのまま、2026-11-14 に `git blame` で確かめた）。
ex 画像を持つ way だけが対象。形は blender-poc の見本（`ingame/switch_ex_shapes.nut`）で敷いて確かめた（2026-11-14、絵は通常のまま）。

| 形 | 線路の引き方 | 使われる絵 |
|---|---|---|
| Y字分岐 | T字の両側の隣（例: `nse` なら北と南）が、そろって枝と反対の側へ曲がるカーブ。1 本が左右対称に 2 本へ開く。枝の隣は `nw`・`sw`・`nsw` 以外 | ex（その T字の向き、`nw` = false。`nse` なら 26 番） |
| 三方分岐 | 十字の両側の隣（北と南、または東と西）が、そろって同じ側へ曲がるカーブ。1 本が 3 本へ開く | ex（1 本側の向きの T字の枠、`nw` = true。北と南が西へ曲がるなら `nse` の 31 番） |
| 渡り線 | 十字の東隣が西–北のカーブで、向きの制限（信号など）で西だけになっている。北隣は北へ、西隣の南隣は南か西へつながる | 十字に ex（`sew`、`nw` = false）、西隣に switch 画像（`nw` = false） |

- 十字の ex の枠（30・35 番）は、線路の自動選択では使われない。三方分岐も渡り線も T字の枠を使う。十字の枠を使うのは道路だけ（`select_switch_road_image`）。
- 渡り線は東隣が西–北のときだけで、左右反対の形はコメントアウトされている。
  西隣に switch 画像を付けるので、西隣は T字を想定していると読める（カーブだと絵の番号が範囲の外になる）。
  `nse` の `nw` = false の絵は 9.2 の表では北–東のカーブで、渡る経路（南–東）と合わない。作者の意図は確かめられていない。
- 列車の予約で switch 画像に切り替わる処理は、ex 画像のタイルでは働かない（`schiene_t::reserve` の `!get_is_ex_image()`）。
- ダイアログの選択肢 3・4 の名前（`gui/ground_info.cc` の「Y-junction」「Double crossover」）は、`128na/simutrans` の改修（2026-11-14）で付けた仮のもの。線路の十字の 3・4 は自動では使われないので、名前は見直す余地がある。
- 敷くときの癖: スクリプトの `build_way` で、カーブになったタイルから 3 本目を足すと、タイルの向きが崩れた（つながらない絵になる）。両側を先に 1 本で通してから枝を足すと正しく敷ける（`OTRPv64_3.exe`、2026-11-14）。
- 実際の絵で確かめた（AMI の `addons/ami/ingame/ex_sample.nut` で敷いた 8 組: 在来線・弾性まくらぎ直結軌道・高速線の通常の版、路面軌道、在来線の基盤 4 版に架線つきの壁を重ねたもの。`OTRPv64_3.exe`、2026-11-21）: Y字分岐・三方分岐とも根元の 4 向きで、自動で選ばれた絵が固定の道具（`tool_set_switch_image` の値 4 = 26〜30、値 3 = 31〜35）の T字の枠の絵と同じになった。温暖・降雪とも。三方分岐の絵は十字のタイル（向き 15）に出るので、十字の道床・壁の上に描く
- 在来線とラダー軌道の高架の版は、地上の版と同じ結果だった（#82）:
  - 敷いた組: 在来線（`ami_rail_ballast`）とフローティング・ラダー軌道（`ami_rail_ladder`）の、高架の各 4 版（`_elev_<版>`）。way-object は重ねていない。
  - 確かめた場所: AMI の `addons/ami/ingame/ex_sample.nut`。高架の way は 2 段上のタイルに乗るので、`square_x(x, y).get_tile_at_height(2)` から絵の番号を読み、固定の道具も同じ高さの座標で使う。

  - これからの種類: 高架の版の way の ex の選ばれ方は、同じ線路の地上の版で確かめれば省いてよい（2026-11-21、ユーザーの決定）。架線つきの壁（way-object）を高架に重ねたときの見た目はこの対象に入らない（way-object の絵の番号はスクリプトで読めないので、画面で見る）
- 高架の 4 版に架線つきの壁を重ねた分岐は、地上の版に重ねたときと同じ絵だった（#85）:
  - 敷いた組: 在来線の基盤の 4 版（`ami_rail_ballast_base_<版>`）と高架の 4 版（`_elev_<版>`）に、同じ版の架線つきの壁（`ami_wall_rail_<版>_catenary`）を重ねた 8 組。way-object は way の乗る高さ（高架は 2 段上）の座標で敷く。

  - 地上の版の架線は way と同じ経路に張られている（#67、[記録](../records/2026-11-21_ami-rail-switch-ex.md)）ので、高架の架線も下の way と同じ経路に張られる。`OTRPv64_3.exe`、`flat_512.sve`、2026-11-21。[記録](../records/2026-11-21_ami-elev-catenary-ex.md)

- 公開版の OTRP は `v63_4`（2026-11-21 から。それまでは `teamhimeh/simutrans` の `v63_3`）。`v63_3` は 9.1 の KUTA_v6 のコミットを含む。`v63_3` と、`128na/simutrans` の `feature/script-save`（`1cc2e78b9`）・`v63_4`（2026-11-21）の間で、選ぶ処理と読む処理のファイル（`boden/wege/weg.cc`・`boden/grund.cc`・`obj/wayobj.cc`・`obj/wayobj.h`・`descriptor/way_desc.h`・`descriptor/way_obj_desc.h`・`descriptor/reader/way_reader.cc`・`way_obj_reader.cc`）の差は、`v63_4` の `weg.cc` の情報表示の 1 行（車両のずれの表示）だけ（`git diff`、2026-11-21）。v63.3・v63.4 でも同じ絵が選ばれると読める（ゲームでは確かめていない）

## 11. くどさの物差し（描き込みの量の目安。2026-11-20、同日に合わせ直し）

AMI の精細化のラウンド（#56）で、描き込みが足りないか多すぎるかを AI が判定するための目安。測るのは `tools/blender/busy_measure.py`（way を敷く前と後を同じ場所・等倍で撮り、差の画素から縁の 1px を削った所だけを測る）。判定には、構造の線（レールの明暗・まくらぎの縁のように 5 画素以上まっすぐ続く線。1 つおきの点線も含む）の画素を除いて測った値（出力の「線を除く」の列）を使う。

| 判定 | 細かさ（等倍、線を除く） | 孤立点（way の画素 1000 あたり、線を除く） |
|---|---|---|
| 物足りない | 0.058 未満 | 5.9 未満 |
| 許容 | 0.058〜0.078 | 5.9〜32 |
| くどい | 0.078 を超える | 32 を超える |

- くどいは、両方が上の境を超えたとき。物足りないは、両方が下の境を下回ったとき
- 決め方: 在来線を描き込みの度合いで 5 段に分けた試作（`addons/ami/blender/calib.py`）を、ユーザーが見て決めた。段 3 がちょうどよく、段 2 も許容、段 4 はくどい（2026-11-20、ユーザーの判断）。境は、隣り合う段の値の中間にした。ラウンド 3〜7 の見た目もユーザーが良しとした（ラウンド 3 は「シャープになった」、4〜6 は「よさそう」）。この判断が全部再現されることを確かめた（記録 `docs/records/2026-11-20_ami-busyness-recalibration.md`）
- 線を除く理由: 最初の物差し（線を除かない値で、境は細かさ 0.059〜0.079・孤立点 6.1〜34、どちらか 1 つが上の境を超えたらくどい）は、構造の線の明暗も数えた。ユーザーが良しとしたラウンド 4〜7（細かさ 0.085〜0.087）が、段 4（0.081）より「くどい」に出た。雪の絵では、孤立点の大半が、手前のレールの暗い側面（1 行に 1px の点線）だった
- 両方で判定する理由: 線を除いても、ラウンド 3 は細かさだけが上の境を超える（0.080。孤立点は 25）。どちらか 1 つで判定すると、ユーザーが良しとしたラウンド 3 が「くどい」になる

- **縮めた画面の作り**（本体 `display/simgraph16.cc` の `rezoom_img`。2026-11-21、#89）
  - 1/2 の画面の絵は、等倍の絵の 2×2 の単純平均で作る。透明な画素は平均に入れない
  - 区切りは、絵の基準位置（dat の位置合わせを足した原点）から偶数の座標にそろう。セル（AMI は 256px で位置合わせ -64,-32、pak128 は 128px で 0,0）の原点から 2×2 で平均すれば、ゲームの絵になる
  - 区切りを 1px ずらすと、孤立点がシートの直線のセルで 2〜125 と大きく変わる
- **繰り返す模様の間隔は、直線の画面で 4px おき（タイル 1 辺に 16 個）にそろえ、タイルの辺の上に置く**（#89、2026-11-21、ユーザーの決定）
  - 3.56px おき（18 本）のまくらぎは、1/2 の格子とずれてうなり、むらのある粒になった（AMI の在来線で 1/2 の孤立点 49。pak128 は 17）
  - 4px おきにすると、どのまくらぎも同じ形に描かれ、1/2 では規則正しい点の並びになる
  - 位置でも値が変わる。辺の上は南北・東西とも良く、辺から半ピッチだと南北が悪い。辺の上なら、向きを逆にした経路でも同じ位置になる
  - スラブの締結装置も、直線だけ同じ置き方にした（`slab_parts.py` の `FASTENER_ACROSS_STRAIGHT`）
  - 斜め・カーブ・坂に合わせた置き方は作っていない。ゲームの見本の斜めのセルでは 1/2 の粒が出なかった。まくらぎの間隔は斜め・坂にも効き、シートの値では坂・斜め・1 タイルだけの絵で 1/2 の孤立点が増えた（ゲームの 1/2 では確かめていない。#132）
