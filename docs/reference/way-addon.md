# way アドオンの知見（本体の描き方・dat の決まり・手本の作り）

線路・道路・側壁・高架・橋・トンネルなどの way 系アドオンを作って分かった「決まり」をまとめる。
本体（Simutrans）と手本（pak128 標準・SIS・iss）の作りを、ソース・画像・ゲームで確かめたもので、このリポジトリのコードを読んでも分からない。

- 作業の手順は書かない。手順はスキル（[way-addon-build](../../.claude/skills/way-addon-build/SKILL.md)・[way-calibration](../../.claude/skills/way-calibration/SKILL.md)）にある
- 調べた経緯は書かない。経緯は `docs/records/` と各アドオンの README にある
- 各項目に「どこで確かめたか」と、数値には測った日付を書く。新しい手本・新しい本体では測り直す

## 2. 本体の描き方と持ち分（どの画素をそのタイルが描くか）

本体は地面を先にまとめて描き、物を奥から描く。カメラは南東にある。

- **平らな部分**: 持ち分は地面の菱形。奥のタイルが手前へはみ出した絵は、手前の平らな地面が先に描かれるので、約 1 行（＋半行）までしか残らない。
  持ち分を 2 行以上ずらすと、継ぎ目に草の線が出る。坂のタイルは地面を後から描き直すので、奥からのはみ出しを消す
- **高さのある部品**（壁・躯体）: 持ち分の全体を上へ広げる。奥のタイルの絵の上に出る（建物と同じ）。
  タイルの境の切り口の面は取る（残すと暗い縦線になる）。輪郭の半透明の画素は捨てる（黒い点線になる）
- **坂の下・床の下が見える絵**: 平地に立つ坂（橋の Ramp）は坂の面から地面まで、坂から始まる橋（Start）は地面を下げた形、高架は床の 1 段下まで
- **坂の面より下を描かない絵**: トンネルの坑口は坂の面だけ（と躯体の高さだけ上）。way や坑口の絵は地面の上に重なるので、
  隣の丘に隠れるはずの面（坑口の高い側の辺の下）まで持ち分に入れると、丘の上にはみ出して見える
- **隣の way とつながる絵**（坑口・橋の端など）: 持ち分の手前の 2 辺は線路と同じ量だけ広げ、つながる部分（床・基盤）は
  隣と同じ基準面に乗せて、タイルの辺まで伸ばす。どれか 1 つ欠けると辺に 1 画素おきのすき間が出る
- **手前/奥**: 東西の線路は北が奥、南北の線路は西が奥。斜めは東寄りが手前。T字は、まっすぐ通る線路に対して決める
- **予想図との差が 0 px** であっても、分かるのは「各タイルが持ち分どおりに描かれている」ことだけ。絵どうしが段差なくつながっているかは別に見る

## 3. 手本の作り（2026-11 時点）

- **SIS・pak128 標準の道路**: 菱形を地面より 1px 下にずらして描き、自分の上の 1 行は奥のタイルのはみ出しで埋める。
  合わせるときは、絵と持ち分を一緒に 1px 下げ、手前の縁を半行広げる
- **線路の新描画位置**（今の pak128・iss）: 下がっているのはレールだけで、道床は地面の位置にある。斜めの絵はタイルの中心に描かれている。
  道床まで下げると、画面で縦向きの斜め（sw・ne）との角に段が出る。道床は地面の位置を基準にし、レールとまくらぎを下げる（横向きの斜めは半分）。
  ただし道床をまったく下げないと、レールが道床の下寄りに見える。blender-poc では道床も 2px 下げて、Rail_100 と同じく道床の中心がレールより約 1px 下になるようにした
- **「Rail_100 は道床ごと 4px 下」ではない**（思い込みが外れた例）。重心は道床の幅や陰で 1〜2px 動くので、レールの位置は明るさの断面で比べる
- **斜めの幅**: 道床・車道・白線は、経路からの距離を直線の 1/√2 にすると、タイルの辺で直線と同じ点を通る
- **Rail_100 が手前の継ぎ目**（2026-11-13）: Rail_100 の道床は奥の辺の近くで上の数行が欠けていて、奥のタイルのはみ出しで埋める作りらしい。
  持ち分を菱形どおりに切った線路が奥に来ると、帯の上側に草の線（15〜28px）が出る。奥側の持ち分を手前の 2 辺へ 1 行と半行はみ出させると埋まる。
  相手の作りに合わせてはみ出しを足すと、他の相手（SIS・道路）との継ぎ目も変わりうる
- **Rail_100 は `ImageUp2` を持たない**。急坂には 1 段の坂の絵が出る
- **坑口の形**（pak128）: タイル全体の箱で、屋根は丘の上面

## 4. 厚みのある絵を画面で下げるときの坂（2026-11-13）

形を手前へ動かして下げると、坂では動いた先の高さが変わり、同じ量でも画面の下げ幅が変わる（手前上がりの急坂で 0.5 倍、手前下がりの急坂で 1.5 倍）。

- レールと道床で動かし方を変えると、坂の向きでレールが道床の片側に寄り、急坂でまくらぎが道床に埋もれる
- どの部品も坂を当てる前に動かす。下げ幅は「地面の上での位置のずれ」（平地と同じ量を動かす。辺で隣と同じ点を通る）と
  「形の高さ・基準位置を打ち消す分」（坂の傾きで割り戻して、画面でちょうどその px）に分ける
- 全部を割り戻すと、急坂と平らなタイルの継ぎ目で道床の縁に 1px の段が出た
- 坂の向きで帯の高さが変わる（急坂の奥側は平地の半分）。px の値は同じ向きの坂どうしか、平地との差で比べる

## 5. dat と本体の決まり

| こと | 決まり | 確かめた場所 |
|---|---|---|
| way の手前の絵 | `frontimage`・`frontimageup`・`frontimageup2`・`frontdiagonal` | `descriptor/writer/way_writer.cc` |
| 雪の絵 | 同じキーの `[1]` | 同上 |
| way の坂の番号 | `imageup[12]` 北が高い・`[3]` 南・`[6]` 東・`[9]` 西 | ゲームで確認 |
| 橋の端 | 坂のタイルから始まる橋は `Start`（平らな絵）、平地から立ち上がる橋は `Ramp`（坂の絵）。2 段は `Start2`・`Ramp2` | `descriptor/bridge_desc.cc` |
| 橋の `Ramp[N]` | 北が高い坂の絵（本体の `slope_t::north` は南が高い坂で、そのとき `S` の絵を使う） | 同上 |
| 橋の `Start[N]` | 南が高い坂のタイルで使われる | 同上 |
| トンネルの `image[N]` | 北が高い坂のタイル | `descriptor/tunnel_desc.cc` |
| トンネルの坑口 | pak128 では 2 段の坂にしか置けない | `bauer/tunnelbauer.cc` |
| 地形の坂の番号 | 角の桁は sw=1・se=3・ne=9・nw=27。1 段の北が高い坂は 36、南 4、東 12、西 28（2 段は 2 倍） | blender-poc の `ingame/*.nut` で確認 |
| 高架 | dat は `system_type=1`。平地に敷くと way は地面の 2 段上（`z+2`）のタイルに乗る（pak128）。スクリプトで高架のタイルに道具を使うときはその高さを渡す | blender-poc の `src/track_elev_*.dat`。`ingame/switch_all.nut` で `get_tile_at_height` を見た（2026-11-14） |
| 近い斜め（1 タイルずらして並べた斜め 2 本。間隔は TILE/√2） | way の `diagonal[close1]`（北西と南東の角の 2 片）・`diagonal[close2]`（北東と南西）。分け合うタイルは十字 1 本の way になり、絵があればこれを使う。絵が無い way では、分け合うタイルに 2 本の way（それぞれ普通の斜めの向き 6・9）が入り、それぞれの斜めの絵を描く。close 用の別の絵が自動で割り当てられることはない | 本家 r12021（`bc593e19b`）、OTRP の `weg_t::check_close_diagonal`（ribi が 4 方向で close の絵があるときだけ）。手元の `makeobj`（60.12）はキーを読む。2 本の way は blender-poc の `ingame/close_diag.nut` で敷いてタイルの中身を読んだ（2026-11-14） |
| スクリプトからの `change_schedule` | 通らない（車両との重なりは手で走らせて見る） | [records](../records/2026-11-13_otrp-script-change-schedule.md) |

見本のスクリプトで坂の向きを逆に指定すると、橋が架からない（絵の問題ではない）。

## 6. 側壁・基盤・バリエーションの作り

- 名前の末尾は `single`（両側）・`back`（奥だけ）・`center`（なし）・`front`（手前だけ）。iss・SIS と同じ並べ方
- 壁: 経路から一定の距離の両側。斜めも同じ作りにする（タイルの辺で直線の壁と同じ点を通る）。
  分岐・十字は、ほかの経路の通り道に入る部分を削る（先の経路の壁を残し、重なった切れ端を消す）
- 基盤: 壁のある側は壁で止まり、壁のない側はタイルの端まで埋まる。経路ごとの板を足し合わせる作りは、分岐で壁を突き抜けた
- 行き止まり: 車止め + 端の壁（タイルの幅いっぱいに作り、残した側壁の外側を削る）。並べると 1 つのコの字になる
- 1 タイルだけの軌道: 全面の基盤だけ（すき間埋めの景観用）
- 高架: 側壁の版 + 橋脚 + 床の 1 段下までの躯体
- 近い斜め: 壁の無い版（本体・旧・試作）は `diagonal[close1]`・`[close2]` を持つ。側壁・高架の版は持たせない。持たせると分け合うタイルが十字 1 本の way になり、奥と手前が同じ版になって 2 本の間に壁が立つ。持たせなければ本体が 2 本の way を置くので、奥の線を back、手前の線を front にできる
- 斜めの基盤の壁の無い側: 中心線から TILE/(2√2)（近い斜めの 2 本の真ん中）より外を削る。タイルの角まで塗ると、隣の線のレールを隠し、隣の線の壁の外へ三角に突き出した。切り口は下ほど中心線へ寄る斜めにする。縦に切ると、奥の線の切り口の側面（暗い）が手前の線の床の上に線で見えた（2026-11-14、ゲームで確認）
- 高架の back・center の斜めには橋脚を描かない。手前にいつも front の線があり、その橋脚で足りる。描くと、画面で横向きの斜めでは柱が手前の線の床に暗い点線で見えた
- 画面で横向きの斜め（`nw`・`se`）では、手前の壁・手すり（`frontdiagonal`）がその線のレールを隠す。壁から外へずれても画面では縦にしか動かず、壁の高さ（約 9px）がレールとの間（約 7px）より大きいため。1 本だけでも同じで、車両を走らせても絵の欠けや重なりは出なかったので、このままにした（2026-11-14、ユーザーが確認）
- 部品の位置は、部品ごとに足し引きせず、乗る基準面（路盤・走行面）に持たせる
  （レールと道床を別々のやり方で動かして、急坂でまくらぎが道床に埋もれた）

## 7. 継ぎ目の自動判定の限界（2026-11-13、道路の絵をわざと 2px 下げて確かめた）

- 2px のずれは、こちらが手前の継ぎ目に出る草の線（23〜43px）で不合格になった
- 模様のずれは、2px 下げても 1.0〜1.5px にしか出なかった（帯を斜めに横切って測るので小さく出る）。模様だけで不合格になるのは、それより大きなずれ
- 中心のずれは、両側の縁が測れて幅がそろう（差 3px 以下）ときだけ当てになる。坂と平地の継ぎ目は参考（坂の帯は手本でも 6px 広く測れる）。
  歩道付きの道路・全面の道床（縁がタイルの角まで届く）、曲がり（片側の縁しか測れない）、幅の違う相手でも参考値。
  幅の違う相手（Rail_100 は道床が広い）では、中心の差は段ではなく作りの違い
- 草の色は、緑が赤・青より 12 以上、青より 40 以上大きい画素とした。歩道の緑がかった敷石は草にしない。地面の違うマップでは確かめ直す
- 一つの継ぎ目には「相手が奥・こちらが手前」と「こちらが奥・相手が手前」の 2 種類がある。はみ出しの決まりが違う相手だと、片方だけに草の線が出る
- 坂の十字の、坂の斜め隣の角のタイルは、予想図が「坂は地面を後から描く」ことを再現していないので、差が出てもゲームの画面が正しいことがある

## 8. 道具の癖（Blender・ゲーム・シェル）

- Blender: 厚みが 0 になる形は、切り抜き（Boolean）で形ごと消える。地面に切り上げるときは上面を少し上で止める
- Blender: 作った直後のカメラの `matrix_world` は更新されていない。向きは `rotation_euler.to_matrix()` から取る
- ゲーム: 急坂のある所へ `gui.jump` すると、画面の縦の位置が見当から大きくずれる（急坂の十字で 64px）
- ゲーム: 坂の見本の斜め隣を崖のままにすると、崖の岩が草の色の判定に掛からず、道床の縁が測れない。角だけ上げた坂にする
- ゲーム: OTRP 本体を手元でビルドした `../simutrans/build/default/sim.exe` は MSYS2 の DLL を使う。`/c/msys64/mingw64/bin` を PATH に足して起動しないと、`libpng16-16.dll` が無いと言って起動しない
- ゲーム: MCP の `run_squirrel` で渡したスクリプトの中の日本語の文字列は、`選` が `u9078` のような形に崩れる。名札（`tool_set_marker`）など画面に出す文字は ASCII にする
- ゲーム: 検証用の `flat2` はフリープレイになっておらず、残高が大きく負のまま。しばらくすると破産し、MCP が応答しなくなったりゲームが終わったりする。フリープレイはスクリプトから切り替えられず、`player_x.book_cash` もシナリオ専用で使えない（2026-11-14）。見本は起動してすぐに敷いて撮る
- シェル: 標準入力で Python に日本語を流すと cp932 で壊れる。heredoc で `\\n` を含む文字列を書くと改行が壊れることがある

## 9. 分岐（switch）の絵（OTRP 専用）

T字・十字の way に、通常の絵のほかに「分岐の向きを示す絵」を持たせる仕組み。標準の Simutrans には無く、OTRP（KU-TA 由来のソース）の本体だけが読む。
本体のソースで確かめたもの: `descriptor/writer/way_writer.cc`・`descriptor/reader/way_reader.cc`・`descriptor/way_desc.h`・`boden/wege/weg.cc`・`boden/wege/schiene.cc`。
詳しい経緯は OTRP 本体の PR（`128na/simutrans` の `feature/switch-image-override`、フォーク元 `teamhimeh/simutrans#810`）にある。

### 9.1 dat のキーと絵の番号

| dat のキー | 絵の番号 | 本体の呼び方 |
|---|---|---|
| `image[nse1]` `image[new1]` `image[nsw1]` `image[sew1]` `image[nsew1]` | 16–20 | switch 画像（`nw` = false） |
| `image[nse2]` `image[new2]` `image[nsw2]` `image[sew2]` `image[nsew2]` | 21–25 | switch 画像（`nw` = true） |
| （今の makeobj では書けない） | 26–30 / 31–35 | ex 画像（`nw` = false / true） |

- 方角の並びは `nse`・`new`・`nsw`・`sew`（T字 4 種）と `nsew`（十字）。手前の絵（`frontimage[...]`）と雪（`[1]`）も同じ並び。
- `image[new2]` が dat にあると makeobj は 26 枚（通常 16 + 分岐 10）を書き、無いと 16 枚で分岐の絵なしになる。**1 と 2 の 10 枚をそろえる**（片方だけ書くと、もう片方は空の絵になる）。
- 本体の判定は枚数だけ。16 枚を超えると switch 画像あり、26 枚を超えると ex 画像あり（`way_reader.cc`）。waytype は問わない。
- ex 画像（26–35）は本体が読むが、`way_writer.cc` のキーは `nsew2` までなので、今の makeobj ではアドオンに入れられない。
  本体の動作確認には、キーを `nse3`〜`nsew4`（検証用の仮の名前）まで足した makeobj を別に作って使った。本物のキー名は決まっていない。
- ex 画像を書ける makeobj は公開されていない（2026-11-14 に確かめた）。
  - `teamhimeh/simutrans` のリリース（v63_3 まで）の添付はゲーム本体だけで、makeobj は無い。
  - OTRP のソースの makeobj は本家 Simutrans 125 の makeobj 60.12 と同じで、キーは `nsew2` まで。
  - KUTA 版の配布物（v6、2021-12-12）もゲーム本体と ja の tab だけで、makeobj は無い。README の分岐の説明は `NSE1`〜`SEW2` の 8 枚だけで、ex には触れない。
- ex 画像の由来: 読む処理と自動で選ぶ条件（9.4）は、`KU-TANS/simutrans` の `53ca75e21`（2021-12-12、KU-TA-Server「KUTA_v6 source」）で初めて現れる。
  KUTA v1〜v6 の改造を OTRP（`37dfb76a8`、2021-03-31）の上に 1 コミットでまとめたもので、それより細かい履歴は公開されていない（KU-TANS の他のブランチ・リポジトリにも無い）。
  本家の Simutrans には無い。同じコミットの makeobj も 26 枚までで、書く側は作られていない。
- 本体が見るのは絵の並び（26 番から `26 + ribi_to_extra + nw * 5`）だけで、キー名は makeobj の中で決まる。
  書く手段が無かったので、既存の pak で使われたキー名がある見込みは低い。それでもキー名を決める前に、OTRP の開発者に一言確かめる。

### 9.2 本体での使われ方

| 場面 | 内容 |
|---|---|
| 自動選択 | 線路（tram を含む）と道路の T字・十字だけ。隣のタイルの形から選ぶ（`select_switch_image`・`select_switch_road_image`）。ほかの waytype には自動選択がない |
| 列車の予約 | 線路は、曲がる経路を取る列車が予約すると、その向きの switch 画像に切り替わる（`schiene_t::reserve`）。固定した分岐は切り替わらない |
| 固定（OTRP の機能） | タイルの詳細ダイアログで、switch 画像を持つ分岐の画像を選べる。選択は保存され、形が変わる・分岐が解消すると自動に戻る。画像が無い選択肢は出ない |

ダイアログの名前と絵の対応。名前の向きは、タイルの中に描かれるカーブが主線のどちらの端につながるか（枝が主線のどちら寄りに出るか）。
ゲームに方角の表示は無いが、画面は地図ごと回るので、方角は画面の向きに固定される（北 = 右上・東 = 右下・南 = 左下・西 = 左上）。ダイアログの名前には画面の向きを添える（例: 「東（右下）へ分岐」）。
自動選択（`select_switch_image`）が `nw` の真偽を選ぶ条件は「隣のタイルがどちらへ曲がるか」で、タイル内のカーブはその手前側（S 字の前半）を描く。
隣の向きで名前を付けると、画面のカーブと逆になる:

| ダイアログの名前 | 絵 |
|---|---|
| 標準 | 通常の絵（`image[nse]` など） |
| 南（左下）へ分岐／北（右上）へ分岐（NSE） | `image[nse2]`（南–東のカーブ）／`image[nse1]`（北–東） |
| 西（左上）へ分岐／東（右下）へ分岐（NEW） | `image[new2]`（西–北）／`image[new1]`（東–北） |
| 北（右上）へ分岐／南（左下）へ分岐（NSW） | `image[nsw2]`（北–西）／`image[nsw1]`（南–西） |
| 東（右下）へ分岐／西（左上）へ分岐（SEW） | `image[sew2]`（東–南）／`image[sew1]`（西–南） |
| 渡り線 A／B（十字） | `image[nsew2]`／`image[nsew1]`（`way_writer.cc` のコメントでは 1 と 2 は「北西–南東が直進」になる別の交差） |
| Y字分岐・三方分岐・渡り線（ex） | ex 画像（今は作れない。選ばれる形は 9.4） |

T字のカーブの向きは、blender-poc の見本（`ingame/switch_auto.nut`）でゲームの自動選択を 8 通りとも確かめた（2026-11-14）。十字の A/B は未確認（`way_writer.cc` の注記から付けた仮の名前）。ずれていたらこの表と本体のラベル（`gui/ground_info.cc`）を直す。

確認の状況（単色の簡易画像で、標準 = 灰・状態 1 = 青・状態 2 = 赤を割り当てて、ゲームで確かめた）:

| waytype | 結果 |
|---|---|
| rail | 実際のアドオンで確認（選択・保存・ロード・形の変化で自動に戻る） |
| tram・monorail・maglev | 実際のアドオンで確認（OTRP 本体の作者による） |
| road・water（運河）・air | 本体のツールで T字・十字とも選択でき、選択ごとに別の絵になることと、詳細ダイアログの表示を確認。air は誘導路（`system_type=0`）と滑走路（`1`）の両方 |
| ex 画像（road・rail） | 検証用 makeobj で 36 枚の way を作り、選択肢 3・4 が別の絵になることと、詳細ダイアログの表示を確認。dat の `3` 系は選択肢 4、`4` 系は選択肢 3 |
| air の滑走路（`system_type=1`） | 本体の建設が T字を許さない（`bauer/wegbauer.cc`: 滑走路は直線と十字の交差だけ）。分岐の絵は十字にだけ使われる |
| 電力（power） | 対象外。電線は `leitung_t`（`obj_t` 派生）で `weg_t` ではないため、この機能の対象にならない |

### 9.3 絵の作りと確かめ方

- 1 と 2 は左右反転ではなく、T字なら枝の曲がる側の違い。持ち分は通常の絵と同じ（2 章）。
- 線路の T字の 1・2 で、タイルの中に描くカーブの向きは 9.2 の表のとおり（枝が隣のタイルでどちらへ曲がるかで選ばれ、タイルの中はその手前側のカーブ）。
- 線路の十字の 1・2 は自動では選ばれない（`select_switch_image` は T字 4 種だけを見る）。タイルの詳細で固定したときだけ出る
- 変えるのは走行面（まくらぎ・レール）だけにし、道床・側壁・基盤は通常の T字・十字と同じにする。
  片側のカーブだけで全部を組むと、カーブの内側に丸い壁が立ち、隣のタイルとつながらない（blender-poc の側壁の版で確認、2026-11-14）
- 道路の自動選択は「隣に T字がある」条件で switch 画像（`nw` = false）を使う（`select_switch_road_image`）。線路と意味が違うので、道路用の絵を作るときは `boden/wege/weg.cc` の条件を読んで合わせる。道路で実物を確かめたアドオンは無い。
- 確かめ方: ゲームで T字を作り、タイルを開いて選択肢を順に選ぶ。スクリプトなら `command_x(tool_set_switch_image).work(pl, pos, "" + wt_rail + ",1")` で選び、`way_x(...).get_image_id()` で絵が変わることを見る（OTRP 本体の自動テスト `test_switch_image_override.nut`）。

### 9.4 ex 画像が自動で選ばれる線路の形

本体の条件は `boden/wege/weg.cc` の `select_switch_image` と `boden/grund.cc` の `is_use_track_wt_ex_image`（どちらも 9.1 の KUTA_v6 のコミットのまま、2026-11-14 に `git blame` で確かめた）。
ex 画像を持つ way だけが対象。形は blender-poc の見本（`ingame/switch_ex_shapes.nut`）で敷いて確かめた（2026-11-14、絵は通常のまま）。

| 形 | 線路の引き方 | 使われる絵 |
|---|---|---|
| Y字分岐 | T字の両側の隣（例: `nse` なら北と南）が、そろって枝と反対の側へ曲がるカーブ。1 本が左右対称に 2 本へ開く。枝の隣は `nw`・`sw`・`nsw` 以外 | ex（その T字の向き、`nw` = false。`nse` なら 26 番） |
| 三方分岐 | 十字の両側の隣（北と南、または東と西）が、そろって同じ側へ曲がるカーブ。1 本が 3 本へ開く | ex（1 本側の向きの T字の枠、`nw` = true。北と南が西へ曲がるなら `nse` の 31 番） |
| 渡り線 | 十字の東隣が西–北のカーブで、向きの制限（信号など）で西だけになっている。北隣は北へ、西隣の南隣は南か西へつながる | 十字に ex（`sew`、`nw` = false）、西隣に switch 画像（`nw` = false） |

- 十字の ex の枠（30・35 番）は、線路の自動選択では使われない。三方分岐も渡り線も T字の枠を使う。十字の枠を使うのは道路だけ（`select_switch_road_image`）。
- 渡り線は東隣が西–北のときだけで、左右反対の形はコメントアウトされている。
  西隣に switch 画像を付けるので、西隣は T字を想定していると読める（カーブだと絵の番号が範囲の外になる）。
  `nse` の `nw` = false の絵は 9.2 の表では北–東のカーブで、渡る経路（南–東）と合わない。作者の意図は確かめられていない。
- 列車の予約で switch 画像に切り替わる処理は、ex 画像のタイルでは働かない（`schiene_t::reserve` の `!get_is_ex_image()`）。
- ダイアログの選択肢 3・4 の名前（`gui/ground_info.cc` の「Y-junction」「Double crossover」）は、`128na/simutrans` の改修（2026-11-14）で付けた仮のもの。線路の十字の 3・4 は自動では使われないので、名前は見直す余地がある。
- 敷くときの癖: スクリプトの `build_way` で、カーブになったタイルから 3 本目を足すと、タイルの向きが崩れた（つながらない絵になる）。両側を先に 1 本で通してから枝を足すと正しく敷ける（`OTRPv64_3.exe`、2026-11-14）。
