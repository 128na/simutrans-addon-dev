# 調査/作業ログ: 全描き直しが約 2 倍かかった原因の切り分けと、描画の時間のログ（#30）

## 目的 / 発端

#375 の作業で 128 の全対象を 2 回描いたとき、2 回目（2129 秒）が 1 回目（1163 秒）の約 2 倍かかった。描画の枠（`SHEET_SLOTS`）の順番待ちか、Blender の失速かを、`render_parallel.py` のログから分けられなかった（[#30](https://github.com/128na/simutrans-addon-dev/issues/30)）。

## 分かったこと（事実）

### #375 の 2 回のログ（作業者の scratchpad に残っていた出力）

- どちらのログにも `[render] 枠待ち` の行が無い。この行は、`--jobs` の上限より少ない数しか動かせず、対象が残っているときに出る。**2 回とも、枠の順番待ちは起きていない。**
- ログにあるのは対象ごとの完了時刻だけなので、「17 番目以降の対象は、16 個前の完了の直後に始まる」として、対象ごとの描画の秒を逆算した（対象は名前順）。平均の同時数は 15.7 と 15.8 で、どちらも 16 本を保っていた。
- 描画の秒の合計は、1 回目 18228、2 回目 33683。**同じ本数の Blender が、それぞれ遅くなっていた。**
- 遅くなったのは一部の時間帯の対象。5 分ごとの完了数は、2 回目が 71・41・36・14・15・15・45・21。たとえば `ami_rail_slab_old_elev_back` は 131 秒が 616 秒、`ami_road_expressway_base_single` は 108 秒が 504 秒。名前順で終わりのほうの対象（歩道・壁）は 1 回目とほぼ同じ秒。
- ログの更新時刻と所要から、1 回目は 08:49:48〜09:09:11、2 回目は 10:33:27〜11:08:56。
- 2 回目の描画の時間帯には、pak256 #175 の作業者のゲーム（見本の敷設と撮影。ログの名前は `scene175-*.log`）が 10:22〜11:04 に流れていた。

### 今回の全描き直し（2026-11-27、main の 258 対象、`--jobs`・`SHEET_SLOTS` は既定）

- 1093 秒。枠待ちは合計 0 秒、描画の合計 17115 秒、CPU の合計 17340 秒。失敗なし。
- 128 の PNG は 1 枚も変わらない（`git status` の `src/` の差分は、控えの `.txt` の改行だけ）。
- 条件: ほかの `render_parallel.py` が終わって Blender が 0 本の状態が 60 秒続いてから始めた。静かではなく、始めから約 13 分は OTRP のゲーム（`sim-WinGDI64-OTRPv64`）が 1〜2 本動き、マシン全体の CPU 使用率は描画の間 81〜100%（20 秒ごとの測り）だった。
- #375 の 2 回目で遅かった対象も、1 回目と同じ速さ（`ami_rail_slab_old_elev_back` などは約 120 秒。まとまりの合計は `ami_rail_slab` が 1 回目 2332・2 回目 7657・今回 2099、`ami_road_expressway` が 966・4176・843）。
- 長い対象の CPU の秒は、描画の秒とほぼ同じ（1 本の Blender が約 1 コアを使い続ける）。短い対象やモノレールのまとまりでは、CPU の秒が描画の秒の 6〜8 割（アイコンの子の Blender の CPU は数えていない。差の内訳は調べていない）。
- 描画の秒は中央値 75、最大 141。長いのは壁の架線付き（`ami_wall_rail*_catenary`。130〜141 秒）と、バラスト軌道の基盤（`ami_rail_ballast*_base_single`・`_base_front`。133〜140 秒）。
- まとまりごとの割合（描画の秒の合計に対して）: 在来の線路の 4 種（バラスト・スラブ・コンクリート・ラダー。各 22 対象）が各 11〜12% で計約 47%、磁気浮上 12%、`ami_wall_rail` 9%。
- 所要 1093 秒に対して、描画の秒の合計 ÷ 16 は約 1070 秒。対象の並べ方（長い物を先に描くなど）で縮められるのは、終わりの約 23 秒までと見積もれる。

### 枠の待ちのログの確かめ

共有の枠と分けた場所（`--slot-dir`）で、`SHEET_ONLY=ns` の 5 対象を描いた。枠 2・上限 4 では、後の 3 対象に待ち 7〜17 秒が出て、枠 8・上限 4 では全部 0 秒。失敗する対象を混ぜた回は、これまでどおり `done in …, failed: …` が最後の行で終了コード 1。

## 推測・未確認事項

- **失速の原因は分かっていない。** 否定できたのは枠の順番待ちと、描く対象の側（今の main では同じ対象が速い。ただし #375 の 2 回目はマージ前のコード）。残るのは、同じ時間帯のほかの負荷など、マシンの側。
- pak256 #175 のゲームとは時間が重なるだけで、原因とは言えない。今回はゲーム 1〜2 本が動いていても遅くならなかった。枠を取らない Blender（直接の `blender -b`）がほかに動いていたかは調べていない。
- 次の候補（未確認）: 描画の Blender は優先度「低」なので、負荷があると遅いコア（i9-12900F の E コア）に回される、または CPU の時間が回ってこない。次に失速したときは、ログの `CPU` と `描画` の秒で分かれる（`tools/README.md` の「描画が遅いとき」）。
- 今回の CPU 使用率が高かった残りの内訳（描画とゲーム以外）は調べていない。

## 次に縮められる所の案（どれも未確認）

1. 失速の切り分け: 次に遅い回が出たら `CPU` の秒を見る。`CPU` も伸びていれば、数対象で `--priority below_normal` と比べる。
2. 長い対象の内訳を測る: 壁の架線付き（約 140 秒）とバラストの基盤を `profile_sheet.py` で。2026-11-17 の測りでは、時間の大半は Boolean だった。
3. 描く対象を減らす: 直した部品が使われる対象だけを描き、全描き直しは最後に 1 回にする。1 回 18 分の全描き直しそのものが一番大きい（進め方の側は別の issue）。
4. 見送り: 並べ方の工夫は約 23 秒しか縮まらない。

## 結果どうしたか

- `tools/blender/render_parallel.py`: 対象ごとの待ち・描画・CPU の秒、開始と終わりの時刻、合計と描画の長い対象を出すようにした。最後の `[render] done in …` の行は形を変えていない（pak256 の `tools/build_ami256.py` が読む）。
- `tools/README.md` の「描画が遅いとき」に見方を足した。
- 絵とアドオンは変えていない。
