# 調査/作業ログ: 景観アドオンの配置例を読み、同じものを敷き直す（#173）

（2026-11-22）

## 目的 / 発端

景観アドオンは、路面電車の軌道を交差点の標示に、運河の停留所を箱積みの駅ビルに使うなど、パーツを本来の用途と違う形で作る。何を表したくてその種類を選んだかが分からないと、パーツの意味を正しく読めない。ユーザーが手本（ISS・SIS など）を手で分析する場として [#173](https://github.com/128na/simutrans-addon-dev/issues/173) を作り、練習の題材を用意した。

- ユーザーが示した観点:
  - そのアドオンが何を表すためのものか。例: Std 版には 4 車線の道路が無く、2 車線を 2 本並べて表す。4 車線どうしの交差点は十字路が 4 つ並ぶだけで見栄えが悪い。専用のアドオンで、スクランブル交差点や右折車線を表せる。
  - なぜ路面電車の軌道を使い、way-object・専用の道路・標識を使わないか。専用の道路は市道化で上書きされる。way-object は道路の形に従う。信号は 1 つに入る部品が少なく、置ける場所も限られる。路面電車の軌道は道路に重ねられ、車の通行を妨げず、1 つに多くの絵を入れられる。
- 題材: 景観アドオンを多く入れた検証用のフォルダの `cityscape_demo.sve`（OTRP v64.3）。
  - 練習 1: ISS・SIS の交差点・ロータリー・高速道路の分岐の配置例 8 つ。ソースが `../refs/` にある。
  - 練習 2: ソースの無いアドオンを含む例 2 つ（(48,9) 付近の街路、(59,9) 付近の箱積みの駅ビル）。

まとめた決まりは [cityscape.md](../reference/cityscape.md) に書いた。

## やったこと

- ゲームを内蔵の MCP つきで起動し、スクリプト（`run_squirrel`）で配置例のタイルごとの way・way-object・標識・建物の名前とつながる向きを書き出した。保存データは触らず、練習 2 はユーザーの保存の写しを読み込んだ。
- 練習 1 は、ISS の dat・画像・作者の図（`../refs/iss/docs/technique/`）と SIS のソースを読み、絵とつながる向きの対応を確かめた。
- 練習 2 は、ゲームの中で物の設定（種類・waytype・system_type・速さ）を読み、空き地に層ごとに敷き重ねて撮り、前後の画素の違いで各層の絵を確かめた。
- 決まりから敷く手順をスクリプトに書き、同じゲームの空き地に複製を敷いた。元と複製の書き出しの差分と、同じ位置から撮った画面で比べた。

## 分かったこと（事実）

### 練習 1

- 8 例すべてで、複製の書き出しが元と一致した（way の名前と向きの差分 0）。画面も一致した。
- 景観パーツは `waytype=tram_track`・`system_type=0` の way で、ゲームで読むと waytype 2（track）・system_type 7（路面電車）。道路と重ねても踏切にならない（本体の `boden/wege/weg.cc` の `needs_crossing`）。
- 絵はつながる向きの 16 通りで選ばれ、作者はこれを位置の番号として使っている。同じ向きで別の絵が要る所は名前の違う way に分けている（ISS の `2-1`／`2-2`、SIS の `F`／`B`）。
- 敷き方の決まり（区間の両端は内向きの 1 方向だけつながる、重ねると向きが足される、1 マスの敷き直しは向きを保って名前が替わる）は、本体の `bauer/wegbauer.cc` の `build_track` と小さな試験で確かめた。
- SIS の高速道路の左の例の 1 回目は崩れた。道路の曲がりのタイルを 1 マスで別の道路に敷き直したら、置き換わらずに向き 0 の道路が足され、その上に軌道が敷けなかった（エラーの文は空）。ランプを外の端からランプの名前で区間として敷き、本線の T字のタイルだけ 1 マスで本線の道路に戻す順に変えて、差分 0 になった。路面電車の軌道の曲がりは 1 マスで置き換わった。
- `draw_as_ding` は ISS が 0、SIS が 1（6 車線の真ん中の列の `M` だけ 0）。1 はタイルに `draw_as_obj` の印を立てる（本体の `boden/grund.cc` の 856 行付近）。

### 練習 2

- (48,9) 付近: 道路 `iss_wrg_0050` を 2 本並べた 4 車線の十字に、運河の歩道、道路の縁を覆う路面電車の軌道、道路と運河の way-object、方面案内の標識を重ねていた。複製は元と画素まで一致した。
  - 標識は、同じタイルにもう一度立てると反対を向いた。元に合わせるには 2 回立てた。
- (59,9) 付近: 地面の歩道（運河）の上に、運河の停留所の箱を 3 段積み、2・3 段目の床に高架の運河を敷いていた。手前の道路には、高架の道路 `Road_Tram_Track_embedded` を重ね、その上に路面電車の停留所を置いていた。複製は、停留所の名前の番号（1 と 8）のほかは元と一致した。
  - 入口の建物（`Hako128_Ent_A-1`、way の要らない付属の建物）は、上に高架を敷いた後では「Tile not empty」で建たなかった。高架の前に建てる順にした。向きは 4 通り試して南で一致した。
  - 元の停留所は 1 つ。運河の建物と路面電車の停留所は 2 マス離れていて、合併の道具は「Too far away to merge stations!」で使えなかった（`allow_merge_distant_halt=2`）。間の歩道に仮の運河の停留所を建てると路面電車の停留所に入り、その後の箱も同じ停留所に入った。仮の停留所を取り除いても 1 つのままだった。
- ユーザーは練習 2 の分析を「正しく分析できている」と評価し、仮の停留所でつなぐ手は「よく使われるテクニック」と確かめた。

## 推測・未確認事項

- 練習 2 の各パーツが「なぜその種類か」（歩道を運河にすると市道化で上書きされず車も入らない、など）は、ユーザーが分析を正しいと評価したが、作者の説明は読んでいない。
- `draw_as_obj` の印で見た目がどう変わるか、ISS と SIS で分けた理由。
- SIS の 4 車線の交差点の中ほどの T字の `F`／`B` の決まり、6 車線の腕の真ん中の列をつなぐ位置の理由。
- 道路の曲がりの 1 マスの敷き直しが置き換わらない原因（`wegbauer.cc` の道路側に、閉じた斜めの 2 本の脚を見分ける処理があるが、追っていない）。GUI でも同じかは未確認。
- `wa-cs-frame-okujou` と `iss_wwe_sidewalk6` の使い分け。上の建物で隠れて違いを確かめていない。
- `AveP_CR_01_3` の「_3」、`tku_SIS_sidegreen_2b`・`1f` の数字の意味。
- way-object の向きはスクリプトで読めない。区間で引いた結果が画素で一致したので同じ向きと見ている。
- ISS の配置例の腕の端にある `iss_wrg_0120_single`（橙の柵）の役割。デモの終端と推測している。
- 元の作者（ユーザー）が GUI でどう操作したか（区間のドラッグの順、標識の向き、高架の高さの上げ、仮の停留所）は確かめていない。
