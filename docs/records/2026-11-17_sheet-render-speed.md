# 調査/作業ログ: シート描画の速度改善（Issue #30）

（2026-11-17。対象は `tools/blender/sheetlib` と blender-poc の 28 枚。基準は blender-poc の `src/` の画像）

## 目的 / 発端

blender-poc の 28 枚を描くのに、並列 16 で 601 秒かかっていた。Issue #30 の案「先に測る → 重い所を直す → 並列数を測る」を順に試した。
改善は絵を変えないこと（描き直したシートが前と全画素同じ。`git status` の `src/` の差分なし）を条件にした。

## 分かったこと（事実）

### どこで時間を使っていたか（`track_wall_back` を単独で描いて測定、225.6 秒）

| 区間 | 時間 |
|---|---|
| 形の組み立て（`assemble`） | 203.6 秒（90%） |
| うち Boolean（298 回） | 192.2 秒（85%） |
| セルの描画 | 15.1 秒（7%） |
| 後処理（`make_sheet`・numpy） | 約 1.5 秒（1% 未満） |

- Issue の「GPU が使われないから」「後処理が重い」という見立ては外れた。描画と後処理は小さい。
- Boolean の内訳は、`bpy.ops.object.modifier_apply` の呼び出しごとに走るシーン更新（約 105 秒）と、演算そのもの（約 117 秒、重なる部分あり）だった。

### 試した案と結果

| 案 | 結果 |
|---|---|
| 1. 通り道の切り抜き形を使い回す | 効果なし（225.6 → 228.1 秒）。形の作成は合計 0.2 秒ほどで、元に戻した |
| 2. `modifier_apply` をやめ、評価した形を新しいメッシュにして差し替える（`core.py` の `_apply_modifier`） | **225.6 → 117.5 秒**。絵は同一 |
| 3. シーンの物の数を減らす | 実装せず。Boolean 1738 回のうち軽い 1516 回は合計 8.5 秒（1 回約 6 ミリ秒）で、物の数による遅れは小さい |
| 4. 並列数 | 下表 |

並列数と所要時間（全 28 枚、案 2 の後）:

| 並列 | 12 | 16 | 24 | 28 |
|---|---|---|---|---|
| 秒 | 335 | 287 | 348 | 313 |

改善前は 16 並列で 601 秒だったので、約半分になった。どの並列数でも `src/` の差分はなかった（全 28 枚が前と同じ）。16 より増やしても速くならない
（案 2 で待ちが演算そのものになり、CPU が飽和した）。`JOBS` の既定は 16 のまま。

### 残りの時間

案 2 の後の 117.5 秒のうち、約 90 秒は 222 回の重い Boolean。板（6 面ほど）を、分岐の通り道の形（約 430 面）で削る処理で、1 回 1.2 秒ほどかかる。
時間は削られる側でなく、削る側の面数で決まる。

## 決まり / 運用

- 共通の道具（`sheetlib/core.py`）で直したので、アドオンごと・セッションごとの考慮は要らない。
- Boolean を足すときは `bpy.ops.object.modifier_apply` を直接呼ばず、`boolean()`・`clip_to_tile()`（`_apply_modifier`）を通す。ops を使うと速くならない。
- 並列数は環境の設定値。PC を替えたときだけ測り直す。
- 新しい分岐の形を足した後など、時間が気になるときは `tools/blender/profile_sheet.py` で測る
  （`SHEET_ONLY=ns,diag_nw,up12 blender -b --factory-startup --python ../../tools/blender/profile_sheet.py -- 対象名` を、アドオンのディレクトリで）。
