# 作業ログ: iss の版ごとのカーブ・分岐の絵の描き分けを AMI に入れるかの検討（#88）

（2026-11-21）

## 目的 / 発端

iss の線路は、版（single・back・center・front）ごとにカーブの描き方（曲線か直線か）と分岐の絵の有無を変えている（`../refs/iss/docs/spec/way.md` の諸元、`../refs/iss/docs/technique/index.md` の「線路とポイント挙動」）。
OTRP で分岐の絵の自動選択・固定・列車の予約での切り替えができるようになった今（`docs/reference/way-addon.md` の 9 章）、この作りを AMI に入れる意味があるかを確かめた。
iss と AMI を同じ配置で敷いて並べ、導入の案を出してユーザーが決めた。

## 分かったこと（事実）

### issue の前提の訂正

- **AMI の線路はどの版も「直線」の作りだった。** 線路 4 種（在来線・弾性まくらぎ直結軌道・ラダー軌道・高速線）の通常の版・基盤 4 版・高架 4 版とも、カーブ・T字・十字・分岐の絵を、タイルの辺の中点を結ぶ斜めの直線で描いている。
  - 確かめた場所: `addons/ami/src/*.dat` の `image[sw]`（通常の版は `diagonal[sw]` と同じセル、基盤・高架の版は別のセル 2.5）と、シートのセル
  - 曲線で描いているのは路面軌道（`ami_tram`）だけ
  - issue の背景にあった「AMI はどの版も曲線」は誤りだった
- **iss で分岐の絵を持たない版は、back ではなく center だった。**
  - 諸元の表は、back を「ポイント画像切替なし」としている
  - 配布されている dat（`../refs/iss/release/pak128/way/rail/track_*.dat`。`src/way/rail/` と同じ内容）では、back と front は `image[nse1]`〜`[nsew2]` を持ち、center は持たない（5 種とも）
  - ゲームでも、固定の道具（`tool_set_switch_image`）は center のタイルで効かず（返り値が空の文字列で、絵が変わらない）、back・front では効いた
  - 諸元の表の名前（`0130`・`0270`・`0500`）は pak の名前（`0120`・`0240`・`0360`）と違い、表が古い。`refs/` は変えない
- iss の back と front は、T字・十字・分岐 1・2 のセル（行 3〜5）が画素まで同じ（`standard_concrete_g_*.png` を比べた）。違うのは基盤の形とカーブのセル
- iss の T字の標準の絵は、枝の両方の向きの線を描く（三角形）。十字の標準の絵も全部の経路を描く。AMI も同じ描き方だった

### ゲームで並べた結果

- 環境と配置:
  - 環境: `OTRPv64_3.exe`、addon_check の `flat_512.sve` をゲームの写し（`addons/ami/work/study_game/47400/`）で開き、MCP のポートは 47400。温暖、等倍
  - 見本: `addons/ami/ingame/curve_switch_study.{sh,nut}`・`curve_switch_train.nut`
  - 並べた組: iss の `iss_wtg_0240_*`、AMI の `ami_rail_ballast_base_*`、AMI の通常の版 `ami_rail_ballast`

| 場面 | iss | AMI |
|---|---|---|
| T字の枝の先がカーブ（側線への分岐） | 自動で分岐の絵（back・front） | 同じ（基盤の版・通常の版とも） |
| 隣り合う 2 本を T字どうしでつなぐ渡り線（信号なし・列車なし） | 自動では標準の絵（X 形） | 同じ |
| 列車の予約（back から渡り線を通って front の駅へ行く編成） | 渡り線の 2 タイルが分岐の絵に変わり、1 本の斜めの渡り線に見える。通った後も、見た 100 秒の間は戻らなかった | 同じ |
| 固定の道具（標準・分岐 1・2） | back・front は効く。center は効かない | 全部の版で効く |
| 単線のカーブ | single は曲線 | 斜めの直線（角で折れる） |

- 固定の道具の効き目は、同じスクリプトの呼び出しの中では `get_image_id()` に出なかった。呼び出しを分けると出た（`curve_switch_study.sh` の `CLASSIFY=1` が、固定と読み出しを別の呼び出しにする）
- 渡り線を `build_way` で敷くと、両端のタイルがその way に置き換わる。3 本の線をそれぞれの way で敷き直すと、つながりを残したまま元の way に戻った
- 複線のカーブ（back が外、front が内で同じ側へ曲がる）では、角の後に back の線が手前の側に来て、基盤の形が合わない（iss も AMI も同じ）。この検討の範囲外

### 読み解き

- iss が複線の版を直線で描くのは、平行の 2 本を斜めの直線でそろえるためと読める（曲線だと内と外の半径が同じになり、角で間隔が開く）。AMI はもう全部の版がこの作りになっている
- center に分岐の絵が無いのは、真ん中の線から両側へ渡り線を出すときに、どちらの分岐の絵でも片側が切れて見えるのを避けた工夫と読める
  - 今の OTRP は、渡り線の T字を自動では標準の絵（X 形）にし、予約のときだけ通る側の分岐の絵にする。なので、center が分岐の絵を持っていても困らない
- 残る違いは single の曲線だけで、分岐の仕組みとは関係しない

## 推測・未確認事項

- 降雪の絵、高架の版、壁・架線を重ねた見た目は並べていない
- 信号で向きを制限した渡り線は敷いていない。本体のコード（`boden/wege/weg.cc` の `select_switch_image`）には、向きの制限で渡り線の T字に分岐の絵を選ぶ条件がある
- 本家 125.0.1 では確かめていない（分岐の絵を使わないので、この検討には関わらない）

## 結果どうしたか

- 導入の案を 4 つ出した。下書きの PR #93 に、比べた画像（`addons/ami/docs/curve_study_*.png`）を添えた
  - A. 入れない
  - B. single の版を曲線にする
  - C. center の分岐の絵を外す
  - D. 曲線の線路を別の種類として足す
- ユーザーの決定（2026-11-21、進捗管理のセッション）: **A（入れない）**。AMI の今の作り（全部の版が直線、全部の版が分岐の絵を持つ）のままにする
- 範囲外の複線のカーブの基盤の件は、進捗管理が別の issue に起票する（ベータの後）
- 本番の `src/`・dat・シートは変えていない。足したのは見本のスクリプトと画像だけ
- 確かめた事実（渡り線の自動選択と予約での切り替え、固定の道具の効き目が出る時点、渡り線を敷くときの置き換え）を `docs/reference/way-addon.md` の 9.2 に足した
