# 調査/作業ログ: ユーザーの目視なしで AMI の絵の欠陥を見つけて直せる範囲を試した

（2026-11-19）

## 目的 / 発端

ユーザーの目視確認が作業の待ちになりやすい。作成済みのアドオン（AMI・blender-poc）を、数値の検査とゲームの画面の読み取りだけで調べ、AMI で見つけた欠陥を直して、どこまで自動で進められるかを確かめた。blender-poc は調査の記録だけで、修正しない。

修正のやり直しは、同じ箇所 5 回まで、1 つのアドオンで合計 20 回までとした。

## 分かったこと（事実）

### 見つけて直した欠陥（AMI）

スラブ軌道の `base_back`・`base_front`・`elev_back`・`elev_front` で、次の絵の奥と手前が入れ替わっていた（雪の絵を含む）。

- `image[sw]`・`diagonal[sw]`・`image[ne]`・`diagonal[ne]`
- `imageup[6]`・`imageup2[6]`

複線の輪では、線路の間に草が見え、外側に基盤がはみ出していた。在来線のシートと塗りの範囲を比べて見つかった。

原因は `slab_fastener` の頂点が多いことだった。`near_camera` は `centre` が真の部品の頂点の重心で手前と奥を決めるので、締結装置が重心をずらしていた。`tools/blender/sheetlib/slab_parts.py` の `slab_fastener` に `centre=False` を付けて直した。

| 修正の回数 | 値 |
|---|---|
| 同じ箇所（スラブ基盤の奥と手前） | 1 回 |
| AMI の合計 | 1 回 |

描き直して変わったシートは、上の 4 枚だけだった。

### 修正前後の比較

修正前の絵は、名前の頭を `amib_` に替えた別のアドオンにした（`amib.pak`）。`src/` の PNG と dat を `work/before/src/` に写し、ファイル名と dat の中の `ami_` を `amib_` に置換して、`makeobj pak256` で作る。

同じ手順で修正前と修正後のゲームを別々に起動し、見本の 208 画面（温暖 104・降雪 104）を撮って画素で比べた。

| 項目 | 結果 |
|---|---|
| 全く同じ画面 | 142 |
| 変わった画面 | 66（基盤と高架の back・front が映る区画だけ） |
| 変わらなかったもの | single・center の区画、橋、トンネル |

温暖側の 104 画面で、草が見える範囲を在来線の見本と比べた（違う画素の数）。

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 合計 | 156,198 | 48,808 |
| 複線の輪（`W2a`） | 13,144 | 0 |
| 良くなった画面 | | 33 |
| 悪くなった画面 | | 0 |
| 変わらなかった画面 | | 71 |

修正後に残る 48,808 画素は、基盤の無い通常の way の 14 画面の分で、修正の前後で同じ値だった。

### 数値の検査（`tools/blender/sheet_audit.py`）

dat が参照するセルを調べる道具を足した。AMI は 34 シート 1,948 セル、blender-poc は 28 シート 2,600 セルを調べた。

修正後の AMI の候補は 12 件で、すべて `ami_wall_rail_{back,single}` と架線つきの版の `backimage[new]`・`backimage[nsw]`・`backimage[nsew]` の小さな点だった。ゲームの十字（見本の原点から `3,37` 付近）で壁の端としてつながるのを確かめ、欠陥ではないと判断した。

### 欠陥ではないと判断したもの（AMI）

- 斜めの架線の長い梁（README の仕様）
- 草地の黒い線（地形の段差）
- 十字の付け根の小さな緑（在来線とスラブで同じで、高架の間の地面）
- 門型橋脚の角の短いブロック（タイル中心の柱が床に隠れた形。位置の計算と一致）

### blender-poc で見つけた点（修正しない）

ゲームでは確かめていない。

| シート | キー | 内容 |
|---|---|---|
| `expressway_{elev,wall}_{back,single}` | `image[sw]`・`diagonal[sw]`（セル 2.0・10.0） | 本体から離れた 2px の点 |
| `expressway_{elev,wall}_{front,single}` | `frontimage[ne]`・`frontdiagonal[ne]`（セル 6.2・14.2） | 全体で 4px だけの迷い点 |
| `tollbooth` | 4 方向（セル 0.0〜0.3） | 柱と屋根の境に 1〜5px の穴 |

### 確かめられなかったこと

- 降雪側の高架の交差部で、一部のタイルに雪の絵が出ず暗く写る。修正前の絵でも修正後の絵でも同じに出るので、今回の修正の影響ではない。シートの雪のセルは通常の絵と別の色になっており、月が替わっても直らなかった。先に撮った修正前の画面では雪の絵が出ていて、差の原因は分かっていない
- 画面を読んで出た確度の低い候補 9 件（`slab_t_BT_T1`、`BT_T1ns`、`BT_B1ns`、`ball_t_BT_B1`、`slab_s_BT_B1` の 2 件、`ball_t_VS_IH`、`slab_t_SE_AFC`、`slab_t_SE_H0`）は確かめていない
- 修正後に画像として読んだのは、変わった 66 画面のうち代表の 5 種類（`W2a`・`B_AFC`・`B_B`・`VB_DE`・`W3`）。残りは画素の数だけで見た
- 走行中の車両との重なり、最後の見た目の判断

## 判断したこと

- 同じ作りの軌道どうしで塗りの範囲を比べる検査が、今回の欠陥に一番効いた。`sheet_audit.py` の `--compare` として残した
- 修正の前後は、同じ手順で別々に撮って比べる。先に撮った画面と比べると、手順の違いが差に混ざる
- 見本の `tool_set_climate` を way を敷く前に動かす案は採らなかった。地形を変える区画で雪が消えた
- 回数の上限と、自動で確かめた範囲を分けて報告することは、スキル `way-addon-build` に書いた
