# 調査/作業ログ: way の ex 画像を pak の直接編集で入れられるか確かめた

（2026-11-19）

## 目的 / 発端

KUTA 版で定義された分岐の追加画像（ex 画像、26–35 番。Y字分岐・三方分岐・複線渡り線）は、makeobj の dat のキーに無い。
専用の makeobj を使わず、pak を直接編集して way に画像を足せるかを確かめる。

## 分かったこと（事実）

### 方法

- 番号と色を描いた単純な絵で way を作り、標準の makeobj（60.12）で pak にした
- 提供用の way の 16–25 番に ex 用の絵を入れ、その画像ノードを対象の way の画像リスト末尾へ Python で写した。画像リストの子の数と `count` を更新した
- 対象は 4 本: 継ぎ足さない `xtest_plain`（26 枚）、`xtest_ex`（36 枚）、`xtest_ex40`（40 枚）、雪ありの `xtest_ex_snow`（36 枚）。手前の絵にも同じ番号を入れた

### pak の構造の確認

- 継ぎ足した後の 26–35 番は、提供用の 16–25 番とバイト列が一致した。元の 0–25 番、ほかの子ノード、way ノードのデータは変わらなかった
- `makeobj list` は継ぎ足した pak を読めた。`makeobj merge` で作り直しても、バイト列は同じだった
- 専用の makeobj で作った 36 枚の pak は手元に残っていないので、その出力との比較はしていない

### OTRP（分岐画像を選べる検証ビルド、2026-11-14 のビルド）

| 確かめたこと | 結果 |
|---|---|
| 読み込み | `has_switch_ex_image()` が 36 枚・40 枚・雪ありで true、26 枚で false |
| 固定（`tool_set_switch_image`） | T字 4 種と十字のすべてで選択肢 3・4 を選べ、絵の id は形の順に連番になった。画面で番号を見たのは選択肢 3 の `nse`（31）・`nsw`（33）・十字（35）、選択肢 4 の `nse`（26）。26 枚の way では 3・4 は拒否された |
| 手前の絵 | 奥の絵と同じ番号の絵が出た |
| 雪 | 雪のマップで、雪用の 31 番・30 番の絵が出た |
| 詳細ダイアログ | 36 枚の T字は Auto・Standard・分岐 2 つ・Y-junction 2 つ。40 枚の十字は Auto・Standard・Crossing 2 つ・Double crossover 2 つ。26 枚は Auto・Standard・分岐 2 つ |
| 自動選択 | Y字の形で 26 番の絵が選ばれた（`nse`。枝を足した直後は標準の絵のままで、タイルの再計算で切り替わった） |
| 36 番以降 | 40 枚の way は読み込めた。選択肢は増えず、値 5 は拒否された |

### 本家 125.0.1

- 同じ pak を addons に置いて起動できた。同じ pak を別名でもう 1 つ置くと、4 本の way すべてに上書きの警告が出たので、読み込まれている
- ユーザーが `xtest_ex`・`xtest_ex_snow` を敷いて確かめた。T字・十字とも標準の絵（14・15 番など）で表示され、雪の絵も出た

## 判断と理由

- 画像ノードを自前で組み立てず、makeobj が作ったノードを写す。画像の形式を makeobj に任せられる
- キー名を決めなくても入れられる。pak にキー名は入らないので、番号の並びだけ合わせればよい

## 確かめていないこと

- 実際のアドオンの絵、保存とロード、列車の予約、線路以外の waytype
