# AMI の道路の Y字分岐・三方分岐の絵（ex 画像）を足した（#210）

## 目的 / 発端

issue 210（第 4 弾、管理 #255）。道路の Y字分岐・三方分岐に専用の絵（ex 画像、26〜35 番）を足し、4×2・6×6 の交差点が塞がって見える問題も直す。鉄道系はすでに ex 画像を持つ（#57・#82・#85）。道路の種類は #209（#257・#259・#260）で決まった。手順は、(1) v64 で道路の ex 画像が自動で選ばれるか確かめる、(2) AMI の道路に描いて継ぎ足す、(3) モノレールの ex 画像の有無を確かめる。

## 分かったこと（事実）

- 手順 1（本体）: OTRP v64（`OTRP-KUTAv6` の `weg.cc`）は、`weg_t::calc_image` が switch 画像を持つ way なら waytype を問わず `select_switch_image` を呼び、道路の KUTA 流の決まり（`select_switch_road_image`）は無い。Y字は T字の両隣が根元と反対へ曲がるとき（`grund_t::is_use_ex_image`）、三方分岐は十字の両隣がそろって同じ側へ曲がるときに、way が ex 画像を持てば選ばれる。本体の変更は要らない（128na/simutrans への起票は要らない）。
- ゲームで確かめた（`sim-WinGDI64-OTRPv64.exe`、`flat_512_left_v64`、`ingame/ex_sample.nut` を道路にも使えるようにして流した）:
  - ex 画像を継ぎ足す前の試し（一般道路 1 種に、既存のセルを指す提供用の way を継ぎ足した）で、Y字・三方分岐の根元 4 向きずつが、温暖・降雪とも、固定の道具（`wt_road`、値 4 = 26〜30、値 3 = 31〜35）の T字の枠の絵と同じ番号になった。
  - ex 画像を描いた後、道路 4 種の通常の版（8 組の検査すべて ok、温暖・降雪）、基盤の版（生活・一般・幹線・高速の single、幹線の back・center・front、高速の front）、高架の版（幹線・一般・生活の single、高速の center。z=2）も同じ結果だった。
  - `[check]` の出力の例（`ex_check.sh`、WAYS に道路を渡す）: `[check] ami_road_trunk_base_back YE=ok 3WE=ok YW=ok 3WW=ok YN=ok 3WN=ok YS=ok 3WS=ok`（`snow` の行も同じ。高架は `z=2`）。ok は、自動で選ばれた絵が、同じ向きの T字を固定した絵と同じで、通常の T字の絵と違うこと。絵の中身（根元の向き・白線）は見ない。
  - 確かめた組は 16 個（通常 4、基盤 8、高架 4）。残り 8 個（高速の基盤の back・center、幹線の高架の back・center・front、高速の高架の single・back・front）は、選ぶ処理が way によらないので同じ結果の見込みで、確かめていない。
- 4×2・6×6 の塞がり: ex 画像を足す前の main の pak（c76ec1c）で、`road_junction_sample.nut`（4×2〜6×6、T4x2・T4x4）を v64 で敷くと、十字はどの交差点・どの道路でも通常の十字（`nsew`）のままだった（v64 の本体が十字を標準の絵にする。reference の 9.3）。ex 画像を継ぎ足した後（一般道路）も同じ。つまり塞がりは ex 画像でなく v64 で直っていて、ex 画像は交差点の絵を変えない。
- 道路の分岐の絵（ex）が無いときの Y字・三方分岐: Y字は通常の T字（`plain`）、三方分岐の形の十字は通常の十字（4 向きとも同じ番号）。
- 絵の作り（`sheetlib/road_ex.py` と `road_sheet` の `ex_switches`）: 経路（路面・壁・基盤）は元の T字・十字のまま、白線と轍だけを替える。腕（T字の本線の両端への 2 本）の形は道路のカーブに合わせた。
  - 一般道路（円弧）: 腕の中心線は円弧。路側線は腕の内側（根元の路側線へつながる）と外側（ほかの腕・通り抜ける道の帯の中に入る所を落とす。Y字では 2 本が合わさる点まで）。
  - 幹線道路・高速道路（斜めの直線）: 同じ作りで、腕は斜めの直線。画面で横向きの斜め（se・nw）は、斜めのセルと同じ画素のそろえ方。
  - 生活道路（L 字）: L 字の腕 2 本は重ねると T字・十字の形そのものになるので、白線は T字・十字の白線（口の点線なし）で、轍だけを Y字・三方分岐の向き（根元と腕をつなぐカーブ 2 本。三方分岐は直進を足す）にした。ex 画像と通常の T字・十字の違いは、白線の口の点線と轍。
- 差分の確かめ: 描き直した 24 枚のシートは、通常の絵のセルが前と同じで、新しいセル（行 0・1 と雪の行 4・5 の列 10〜13）だけが変わった（HEAD の PNG と画素で比較）。アイコンは `icons.py` を流し直した（変更なし）。
- 道路の way-object の壁は分岐の絵を持たず、基盤の版に重ねた Y字・三方分岐でも通常の T字・十字の壁が出た（画面で確認。幹線の single・back）。
- 256（#261）: 道路 24 枚を 256 でも描き（`SHEET_PAK_SIZE=256`、約 3.5 分）、`SCALED_TARGETS` の全 213 対象を描いて `CHECK_256_FULL=1 bash addons/ami/check.sh` が全部通った（空のセル・アイコン・踏切・車庫・盛土・256 の pak の組み立て）。256 の pak に ex 画像の継ぎ足しが 24 個入ることは、同じ検査の 128 側（提供用の way 24 個）と、256 の dat・シートが全部そろった状態の build で確かめた。コミットする 256 の PNG は生活道路（`ami_road_local.png`）だけ。画面は 256 では見ていない（128 の絵と同じ式で描いた。`pak256poc` のゲームでの確認は #261 の手順のとおりで、今回は未確認）。
- モノレール（手順 3）: iss（`iss_monorail_way.pak`・`iss_maglev_way.pak`）の way も AMI の跨座式・懸垂式も 26 枚（分岐の絵まで）で、ex 画像（36 枚）は無い。`ex_graft.py --list` で数えた。v64 は way の種類を問わず選ぶので、足せば選ばれるはずだが、ゲームでは確かめていない。

## 推測・未確認事項

- 画面で見た絵は、通常の版（4 種）と、幹線の基盤・降雪の一部。高架の版は絵の番号の確認だけで、画面は見ていない。
- 一方通行・信号などで ex 画像が選ばれない形、橋・トンネルの上は見ていない。
- Y字・三方分岐の絵がどう見えるか（白線の形、轍）は、ゲーム内の見た目の確認（check:user）。
- 本家 125.0.1 での読み込みは確かめていない（ex 画像を継ぎ足した pak は 9.5 のとおり本家でも読める）。

## 結果どうしたか

`tools/blender/sheetlib/road_ex.py` と `sheetlib.py` の `road_sheet`（`ex_switches`）、`addons/ami/blender/render.py`（道路のプロファイルに `ex_switches`）、`addons/ami/blender/ami_dat.py`（`EX_WAYS` が道路の waytype を拾う）、`ingame/ex_sample.nut`（道路を `wt_road` で読む・固定する）、24 枚の道路のシート、生活道路の 256 のシートに反映した。reference の 9.3・9.4 と README（「道路の ex 画像」）を直した。確認画像は `addons/ami/docs/road_switch_ex_<種類>.png`。
