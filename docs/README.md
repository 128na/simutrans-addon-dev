# ドキュメント規約

このリポジトリのドキュメントは「実装とテストが SSOT（唯一の真実）」を前提に、
md として残すものを次の3種類に限定する。この規約は [docs-lint](https://github.com/128na/docs-lint)
パッケージで機械検証される（`npx docs-lint`）。

## 原則

1. コードを読めば分かることは書かない。
2. 残すのは「意思決定の理由」（`docs/adr/`）と「過去時点の記録」（`docs/records/`）だけ。
   どちらも書いたら変更しない（リンク先パスの追従のみ例外、後述）。
3. 変化する事実（ステータス・日付・採番）は台帳に集約し、md 本文には書かない。
4. 手動維持の索引は持たない。一覧は `ls docs/records/`（日付順に並ぶ）で得る。

## 判断フロー

```
書こうとしている内容は…
├─ コードやテストを読めば分かること      → 書かない（実装が SSOT。ただし下記「delete前の確認」を参照）
├─ 「なぜこう決めたか」という理由        → docs/adr/
├─ ある時点の調査・作業・障害の経緯      → docs/records/（日付プレフィックス、以後不変）
├─ 変化し続けるステータス・一覧・採番    → 台帳（既存台帳の行として。新台帳は policy 登録が必要）
├─ 外部（本体・手本・道具）を調べて分かった決まり → docs/reference/（知見。生きた文書として allowlist に登録）
├─ 作業の進め方（どのツールをどの順で回すか）     → スキル（.claude/skills/）。決まりは書かず reference を引く
└─ 常に最新であるべき手順・規約          → 生きた文書（allowlist 追加 = policy 編集 + 理由を ADR に）
```

## 「実装が SSOT」を削除の言い訳にする前に

「コードを読めば分かる」は思い込みで成立していないことがある。複数リポジトリへの実地適用で、
実在するクラス名を含みながら内部構造・メソッドシグネチャ・データ構造が実装と全く異なる
「一見実装がありそうで実は架空」の文書が繰り返し見つかっている。現在形の spec 相当文書を
削除する前に:

1. **対応する実装が実在するか確認する**。存在しなければ削除しない。`docs/records/` へ日付付きで
   凍結する（設計提案・調査中の記録として）。
2. **内容が実装と一致するか確認する**。クラス名が実在するだけでは不十分。文書が挙げる
   具体例のうち最低1つは実際のソースファイルを開き、クラス構成・メソッドシグネチャ・
   データ構造まで突き合わせる。
3. **テストが仕様の主張を実際に検証しているか確認する**。テストファイルの存在ではなく、
   仕様が記述する分岐・バージョン差異の量に対してテストケース数が見合っているか照合する。
   名ばかりのテストしかない場合は、テスト拡充が先か、当面は生きた文書として残すかを判断する。
4. **原理的にテストが検出できない契約でないか確認する**。次の2種は生きた文書 allowlist の
   正当な例外として認める:
   - 外部フォーマット/外部APIの reverse-engineering 文書（自リポジトリの実装を読んでも
     意味論が伝わらない外部仕様）
   - 自動検証のない人手同期の契約（「A を SSOT として B を手動で追従させる」という決定を
     実装・テストのどちらも強制していない場合）

   いずれも allowlist へ追加する際は理由を ADR に残す。

## 分類と置き場所

### 不変記録 — docs/records/

- 命名: `YYYY-MM-DD_slug.md`（例: `2026-08-24_ingest-latency-survey.md`）
- 対象: 調査メモ / 作業ログ / postmortem / 実験結果 / 未実装の設計提案の凍結
- 作成後は変更しない。内容を更新したくなったら**新しい日付で新規作成**し、
  旧ファイル冒頭に `> Superseded by:` + 新記録への相対リンク、の1行だけを追記する。
  もう1つ許可される編集は、参照先ファイルが移動・削除された際の**リンクパスのみの追従**
  （主張・内容は変えず、リンク先を現在の場所や後継 ADR に向け直すだけ）。
  内容の書き換えは一切許可しない。
- 不変であることが信頼の根拠になる。「その日付時点で真だったこと」しか主張しないので、
  古くなってもドリフトしない。
- テンプレ: [templates/record.md](templates/record.md) / [templates/postmortem.md](templates/postmortem.md)

### 意思決定記録 — docs/adr/

- 命名: `NNNN-slug.md`（連番4桁、例: `0001-use-sqlite.md`）
- 「なぜ」だけを書く。「どうなっているか」は実装を参照させる。
- ステータス行 `> ステータス: Accepted (YYYY-MM-DD)` が必須（lint 検査対象）。
  覆すときは新 ADR を書き、旧 ADR のステータスを `Superseded by ADR-NNNN` に変える。
- テンプレ: [templates/adr.md](templates/adr.md)

### 台帳 — docs/dependency-debt.md ほか

- 変化する事実の SSOT。行の追加・更新・削除が正規の運用。
- [dependency-debt.md](dependency-debt.md) のスキーマは変更禁止（`/dependabot-maintenance` スキル互換）。
- 新しい台帳を作るには `tools/docs-policy.json` の `ledgers` への登録が必要。
- md 表で足りない場合（機械読み取り・環境間同期が要る場合）は **yaml を SSOT** にし、
  md は経緯の物語に徹する（例: `known_risks.md` + `risk_ledger.yaml` のペア構成。
  md 側に「ステータスの SSOT は yaml。md 内のマーカーは表示用」と明記する）。

### 生きた文書 — allowlist 制

- `tools/docs-policy.json` の `livingDocs` に列挙されたファイルのみ許可。
- allowlist へ追加する場合は、追加理由を ADR として残すこと。
- 生きた文書は「常に現在を反映する義務」を負う。義務を果たせない文書は
  records 化（日付を付けて凍結）するか削除する。

### リファレンス（知見）— docs/reference/

- 命名: `<主題>.md`（例: [reference/way-addon.md](reference/way-addon.md)）。主題ごとに 1 ファイルにまとめ、数を増やさない。
- 書くもの: このリポジトリのコードを読んでも分からない決まり。本体（Simutrans）・手本のアドオン・道具（Blender など）の
  作りを、ソース・画像・ゲームで確かめたもの。各項目に確かめた場所を書き、測った数値には日付を書く。
- 書かないもの: 作業の手順（スキルへ）、調べた経緯（`docs/records/` へ）、このリポジトリの実装の説明（コードへ）。
- 生きた文書なので、ファイルごとに `livingDocs` への登録が要る。決まりを確かめ直したら、ここを直す。
- 理由は [ADR 0001](adr/0001-reference-docs-separate-from-skills.md)。

### アドオンの README — addons/<addon-name>/README.md

- 今の状態だけを書く。経緯は `docs/records/`、ほかのアドオンでも使える決まりは `docs/reference/` へ。決まりは [addons/README.md](../addons/README.md)。
- docs-lint の検査の対象外なので、区切り（PR のマージ、試作の終わり）で人が見直す。

### スキルとリファレンスの分け方

| | スキル（`.claude/skills/<名前>/SKILL.md`） | リファレンス（`docs/reference/<主題>.md`） |
|---|---|---|
| 中身 | 作業方法: 進め方、回すツールと順番、直す場所、確かめ方、作業の注意 | 知見: 確かめた事実と決まり、その根拠 |
| 読む人 | Claude Code（作業のきっかけで読み込む） | すべての作業者（Codex・人も読む） |
| 分かったことの書き先 | 手順が変わったとき | 決まりが分かった・変わったとき |

- スキルに決まりを書き写さない。リファレンスへのリンクで引き、「作業の前に読む」と書く。
- スキルの名前は作業を表す（`…-build`・`…-calibration`）。`…-reference` という名前のスキルは作らない。
- 迷ったら「その作業をしない人にも役立つか」で決める。役立つならリファレンス。

## 禁止事項（lint がエラーにする）

- allowlist 外の「現在形 md」を docs/ やルートに置くこと
- `temp` / `tmp` / `draft` / `wip` という名前のディレクトリ（下書きは PR 説明・issue・セッションの scratchpad へ）
- `INDEX.md` / `index.md` / `TODO.md` というファイル名（索引は持たない、タスクは台帳か issue へ）
- リポジトリ外への絶対パスリンク（`~/`、ドライブレター、`file://`）
- 壊れた相対リンク

## 検証

```bash
npx docs-lint
```

CI（`.github/workflows/docs-lint.yml`）でも同じものが走る。
